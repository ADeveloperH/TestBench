## 三、数据结构

### 3.1 测试用例

```json
{
  "id": "ie_adjust_revenue_fail",
  "name": "Adjust 收入回传监控",
  "description": "MAX 和 TopOn 的收入回传都成功送达 Adjust 才判定通过；缺少任一成功日志时保持监控中",
  "scope": {
    "global": true,
    "apps": []
  },
  "group": "广告",
  "enabled": true,
  "rules": []
}
```

字段约定：

- `id`：稳定、唯一、发布后不随意修改。激励框架用例使用 `ie_` 前缀，插件或 SDK 用例使用来源前缀。
- `name`：用户在测试侧栏看到的名称，应说明被监控的功能。
- `description`：说明判定依据和排查范围，不要只重复名称。
- `scope.global`：`true` 表示适用于所有已选应用；不是“读取所有系统 PID”。
- `scope.apps`：非全局用例的应用包名列表。
- `group`：按功能模块分组，例如 `广告`、`网络`、`埋点`、`反作弊`。
- `enabled`：可选，`false` 时用例显示“未启用”。
- `requirePass`：可选，`true` 时必须观察到全部 `pass` 规则，未齐全时显示“疑似”。适合必须看到完整成功闭环的监控用例。
- `rules`：规则列表。规则之间不是“任意一条成功”，`pass` 规则需要全部满足才算通过。

### 3.2 规则和条件

```json
{
  "effect": "error",
  "description": "接口请求使用了无效 eCPM（ecpm=0）",
  "expr": {
    "kind": "group",
    "op": "and",
    "children": [
      {
        "kind": "cond",
        "cond": {
          "field": "tag",
          "op": "equals",
          "value": "Unity"
        }
      }
    ]
  }
}
```

当前支持：

- 条件字段：`message`、`tag`、`level`
- 操作符：`contains`、`not_contains`、`equals`、`not_equals`、`regex`
- 条件组合：`and`、`or`
- `effect`：`error`、`warn`、`pass`
- `minCount`：整次测试累计至少命中 N 次才触发，当前没有时间窗口
- `absence`：锚点出现后，在指定秒数内没有出现目标条件时触发缺失判定

设计要求：

- 能确定 Tag 时优先加 `tag=equals`，不要只用 message 关键字。
- 业务错误要同时限定模块 Tag、关键字和必要的级别，避免 SDK 普通日志误报。
- 正常流程用 `pass`；异常流程用 `warn` 或 `error`，不要把所有 Error 级别日志都当成业务失败。
- `regex` 需要测试正例、负例和边界值，例如 `0` 不应匹配 `0.1`，`-1` 不应匹配 `-10`。
- 多个 `pass` 规则表示多个成功信号都必须出现，适合 MAX/TopOn 这类闭环监控。

## 四、状态语义

当前有 5 种状态：

| 状态 | 计算规则 |
|---|---|
| `未启用` | `enabled=false` |
| `有问题` | 命中任意 `error`，或缺失判定超时 |
| `疑似` | 未命中 error，但命中任意 `warn` |
| `通过` | 存在 `pass` 规则，且所有 pass 规则都命中 |
| `监控中` | 没有明确错误、警告，或成功条件尚未全部满足 |

如果用例设置了 `requirePass=true`，成功条件尚未全部满足时会显示“疑似”，即使还没有命中 `warn`。这表示“尚未观察到完整成功信号”，不表示已经捕获到明确错误。

实际优先级为：

```text
未启用 > 有问题 > 疑似 > 通过 > 监控中
```

新一轮测试开始时，所有启用用例通常先显示“监控中”。纯异常监控用例在没有异常时会一直保持该状态；带多个 `pass` 规则的用例在成功信号全部出现后才变为“通过”。

以 `ie_adjust_revenue_fail` 为例：

```text
开始监控             -> 疑似
只出现 MAX 成功日志   -> 疑似
只出现 TopOn 成功日志 -> 疑似
两条成功日志都出现    -> 通过
```

只有需要成功信号闭环的用例才设置 `requirePass=true`，不要把所有用例的初始状态都改成“疑似”。

## 五、新增用例流程

### 1. 先确认日志来源

- 在 `/Users/shareit/RiderProjects/IncentiveEngine`、`/Users/shareit/UnityPlugin`、`/Users/shareit/AndroidStudioProjects/AndroidADLibrary` 和相关 `middleground` 仓库中定位日志调用点。
- 在完整日志中确认实际 Tag、级别、消息格式、是否多行，以及同一关键字是否会正常重复出现。
- 只有源码可达且日志能稳定代表业务语义时，才进入内置用例。

### 2. 决定新增还是扩展

- 同一功能已有用例时，优先扩展现有用例，避免多个用例重复报告同一问题。
- 需要多个成功信号全部出现时，用一个用例配置多条 `pass` 规则。
- 只有在规则效果、排查对象或状态语义明显不同的时候，才新增用例。

### 3. 同步两份内置来源

先修改 `src/features/testcases/engine.ts`，再把同一用例同步到 `config/remote-config.json` 的 `testCases` section。检查 `id`、Tag、关键字、规则效果、分组和 scope 完全一致。

### 4. 用样例回放

至少验证：

- 正常日志命中预期规则。
- 异常日志命中预期规则。
- 相似但正常的日志不会命中。
- 多条命中日志都能在侧栏展示并定位。
- 测试用例页面不受普通日志 Tag 屏蔽影响。
- 切换应用、重置测试和重新启动后的状态符合预期。

### 5. 本地验证

```bash
node scripts/validate-config.mjs
pnpm exec tsc --noEmit
pnpm build
git diff --check
```

开发版 `pnpm tauri dev` 启动时默认读取仓库内的 `config/remote-config.json`，适合先验证新增用例；正式发布前再通过管理页生成、校验和发布远程配置。

## 六、发布和用户更新

- 调试版生成远程 JSON 时使用当前生效的内置与本地用例。
- 发布后，正式版用户会在远程配置缓存过期后的下一次启动自动拉取；当前缓存时间为 5 小时。
- 用户手动刷新配置可以立即拉取。
- 远程 `testCases` 整段替换内置定义；本地自定义用例仍保留，内置用例以远程最新定义为准。
- 发布前必须确认本地自定义用例是否应该进入公共内置配置，避免把个人临时规则发布给所有用户。
- 配置发布和应用版本发布是两条链路：仅修改远程 JSON 不需要发版；修改代码兜底或引擎能力才需要应用版本发布。

## 七、当前能力边界

- 测试 Tab 会先按目标应用 PID 过滤，`global=true` 不会读取系统进程日志。
- `minCount` 只统计整次测试累计次数，不支持“最近 N 秒内连续失败 M 次”。
- 缺失判定必须有稳定锚点；没有测试结束事件时，无法严谨判断“整个测试期间从未出现”。
- 多条 `pass` 规则只证明这些成功日志在本轮都出现过，不关联同一个广告位或同一个 `adPid`。
- 远程配置 section 整段覆盖，因此远程文件被删除某个内置用例后，正式版会以远程结果为准。
