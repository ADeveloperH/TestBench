## iOS Fruit 试点（2026-11-16）

正式 iOS 日志页的“+ → 测试用例监控”提供两条固定只读试点：Fruit 关卡完成信号与 Fruit 进度输出。必须先选中并精确采集 Fruit Quest（`com.lucky.fruit.quest.master` / FruitQuest），再创建测试 Tab；从创建时刻之后开始监测。重新采集或应用重启后重新开始一轮，不回放历史作为新命中。

- 试点定义在 `src/features/ios/iosPilotCases.ts`，不加入 Android 内置身份集合，不随现有用例配置编辑、恢复或导入导出；不要把试点描述为已全量适配现有 Android 规则。
- 共用 `testCaseEvaluation.ts` 的条件匹配后计数及结果状态逻辑，iOS 独立输入保留原文/来源，正文可使用已验证的编码还原；不伪造 Tag 或 Android 字母级别。两条正向试点本身没有缺失或多事件顺序断言；第一批18项候选中的框架初始化已独立接入60秒缺失计时。
- “关卡完成”仅表示出现 `[LevelFlow] step=on_game_win_invoked`；“进度输出”仅表示出现 `[InLevelAdReward]` 的合法0～100%进度文案。它们不能代表服务器结算、广告奖励或整个游戏流程正常。
- 普通筛选、降噪、暂停展示、清空展示与后台 Tab 不停止监测。侧栏“重置全部”/“重新开始测试”开启新轮，单条重置只对后续新记录计数。停止/断线保留本轮证据并提示结束，下一采集会话不自动沿用结果。
- 命中可定位或查看原始证据；记录不在当前窗口时显示保留详情及说明，不跳到其他会话。试点不修改现有 Android 用例 ID、启停覆盖、作用域、规则树、缺失判定和恢复语义。

普通构建默认启用两条 Fruit 正向试点和三十一项业务用例的已验证分支。Fruit 实际采集验证了七项，分别监测 SDK 初始化成功、用户信息初始化成功、道具初始化成功、反作弊设备指纹就绪、缺少 `levelConfig`、iOS 云控 `AddBizKVChangedListener` 明确降级、Beyla 未初始化。Unity 主线程调用违规在独立 iOS 测试包中实际触发了引擎异常，普通构建仅匹配 UnityFramework 首行里明确的 UnityException 主线程错误签名。广告与奖励新增开启广告插件已实证的配置诊断、广告奖励降级和奖励接口失败。独立 iOS 测试包可通过受控输入运行业务逻辑，结合正常对照、真机原文、判定结果与 Android 业务语义核对作为开启依据。网络响应异常、激励框架网络请求失败和关卡或升级流程异常已通过独立包真机验证，沿用 Android 的业务文案和严重度，并按 iOS 的应用和日志来源约束执行。广告 eCPM 异常默认监测专用广告价格上报 POST 请求的完整正文，仅顶层数值 ecpm=0 对应有问题。SDK 与归因五项按真机已验证分支启用。埋点与反作弊的 Foundation 日志继续受各用例来源前缀约束。任务与资源默认开启四项已验证分支，包括本地化资源、UI 资源、存档与文件操作、任务配置接口明确返回失败。任务配置正常响应中未下发对应条目仍可走兜底，该分支留在内部验收。账号业务默认开启 NetworkManager 明确报告的 600 拦截，以及 UserDataManager 与 Withdraw 的已验证失败诊断。验收仅使用包内替身，无真实提现请求。任务系统配置或执行异常仅默认启用每日关卡里程碑的明确领取请求异常。SDK 初始化的 60 秒缺失判定及其余未纳入分支仅在内部验收构建运行，激励框架兜底异常候选在普通构建停用。内部构建继续通过 `VITE_ENABLE_IOS_BUSINESS_CANDIDATES=true` 开启完整 34 项，iOS 仍使用独立只读定义和原有的应用、设备及会话约束。真机证据见 [iOS 验收记录](iOS/iOS业务候选真机验收-20261118.md)。

普通和内部构建均监测 MAX 包 TopOn 验证和 UA 埋点监控，应用范围仍由 iOS 测试 Tab 的 Fruit 精确会话约束。MAX 包 TopOn 验证按会话累计两类证据，要求 MAX 展示事件的顶层 JSON `source=DirectSDK` 与 TopOn 收入明确的预期去重；信号未齐保持监控中，同一轮通过只代表观察到两类信号。UA 用例沿用 Android 缺正向证据显示疑似的状态，只认 Adjust SDK 调用后的「已转发 Adjust 事件」。两项均接受对应库前缀的 Foundation 输出及真机验证的 UnityFramework 探针输出，截断记录不参与判定。

MAX/TopOn 广告收入调用 Adjust 在两条 SDK 调用日志齐全时通过，明确丢弃、收入对象创建失败、未知来源或队列溢出优先判有问题。等待就绪、GreenGame 正常去重及收入统计埋点不会改变状态。Firebase 两路和 Adjust 后台到账证据继续记账。

iOS「无崩溃」监测当前精确应用测试轮次内 Apple `.ips` 明确报告的 `EXC_CRASH / SIGABRT`，相同 incident 只计一次。正常退出和断线无告警，未观察到匹配的报告时保持监控中。

第一批集中开发（2026-11-16）：18项独立Unity业务候选（含既有B批4项）定义在 `src/features/ios/iosUnityBusinessDefinitions.ts`，由 `iosBusinessCases.ts` 绑定固定iOS应用及开关，默认停用、不计数或保留证据；描述明确待集中业务验收。内部构建设置 `VITE_ENABLE_IOS_BUSINESS_CANDIDATES=true` 可开启，普通设置不增加开关、不持久化、不改Android内置身份或远程配置。与两条正向试点合计20项；逻辑/历史原文回放通过不等于完整业务验收。

初始化缺失以接收侧单调时钟计60秒；仅同会话持续采集中、队列已排空且日志完整时检查。源缺口/正文隐藏或截断/无法还原、计时调度停顿超过5秒会保守暂停缺失并提示重新开始。启停命令进行中暂缓告警，停止/断线不继续计时，同会话尾批仍可补成功；触发缺失时可查看锚点原文，不把锚点计为成功目标命中。Android原有定时器/规则和运行状态语义不变。

相关回归：`node --test scripts/tests/ios-unity-business-batch.test.mjs scripts/tests/ios-business-cases.test.mjs scripts/tests/ios-pilot-monitoring.test.mjs scripts/tests/ios-workspace-tabs.test.mjs scripts/tests/test-case-config.test.mjs`。动态测试状态/证据不持久化。

## 配置管理与批量操作

- 设置 → 测试用例支持“全部 / 内置 / 非内置”来源过滤；非内置包含新建及导入用例，来源按当前内置注册表 ID 判断，不按分组名称判断。
- 行选择框用于批量选择；独立的启用开关控制是否启用。全选覆盖当前筛选结果（包含折叠分组）；切换来源时清空选择。
- 支持启用选中、停用选中和删除选中。正式版删除时保护内置用例，调试版仍采用删除名单；删除确认显示实际删除和跳过数量。
- “恢复为仅内置用例”不受列表过滤影响：删除全部非内置用例，清除启停覆盖和调试删除名单，恢复当前生效内置定义及其默认启用状态。它不回退其他配置，也不等同于侧栏的“重置全部”监测状态。
- 本地存储采用版本化配置，将非内置用例、内置启停覆盖及删除名单一起保存；首次读取兼容旧 `logcat-testcases-v4` 与旧调试删除名单。
- 内置启停覆盖在重启和刷新配置后保留；内置规则仍来自最新注册表。本轮不引入完整规则覆盖功能。
- 导入保留内容去重；同 ID 不同内容生成新的本地 ID，避免多个用例共享运行状态。已有 version 2 导入导出格式继续兼容。
- 删除用例或改变规则/作用域后清理其会话运行缓存；仅修改显示名称不影响监测结果。
- 配置回归测试：`node --test scripts/tests/test-case-config.test.mjs`，覆盖旧缓存迁移、启停覆盖、恢复默认、内置保护、导入冲突及运行指纹。

这份文档是后续新增、修改和发布内置测试用例的操作入口。它说明测试用例的结构、状态语义、代码位置、配置同步关系和验证流程；具体业务规则仍需要回到源码和运行日志确认。

## 三、数据结构

### 3.1 测试用例

```json
{
  "id": "ie_adjust_revenue_fail",
  "name": "max/topon 价值回传",
  "description": "MAX 和 TopOn 的价值都成功回传 Adjust 与 Firebase 才判定通过；缺少任一成功日志时显示疑似",
  "scope": {
    "global": true,
    "apps": []
  },
  "group": "广告",
  "enabled": true,
  "rules": []
}
```

字段约定：

- `id`：稳定、唯一、发布后不随意修改。激励框架用例使用 `ie_` 前缀，插件或 SDK 用例使用来源前缀。
- `name`：用户在测试侧栏看到的名称，应说明被监控的功能。
- `description`：说明判定依据和排查范围，不要只重复名称。
- `scope.global`：`true` 表示适用于所有已选应用；不是“读取所有系统 PID”。
- `scope.apps`：非全局用例的应用包名列表。
- `scope.excludedApps`：可选；全局用例需要排除的应用包名列表。排除规则优先于
  `scope.global` 和 `scope.apps`。
- `group`：按功能模块分组，例如 `广告`、`网络`、`埋点`、`反作弊`。
- `enabled`：可选，`false` 时用例显示“未启用”。
- `requirePass`：可选，`true` 时必须观察到全部 `pass` 规则，未齐全时显示“疑似”。适合必须看到完整成功闭环的监控用例。
- `rules`：规则列表。规则之间不是“任意一条成功”，`pass` 规则需要全部满足才算通过。

### 3.2 规则和条件

```json
{
  "effect": "error",
  "description": "接口请求使用了无效 eCPM（ecpm=0）",
  "expr": {
    "kind": "group",
    "op": "and",
    "children": [
      {
        "kind": "cond",
        "cond": {
          "field": "tag",
          "op": "equals",
          "value": "Unity"
        }
      }
    ]
  }
}
```

当前支持：

- 条件字段：`message`、`tag`、`level`
- 操作符：`contains`、`not_contains`、`equals`、`not_equals`、`regex`
- 条件组合：`and`、`or`
- `effect`：`error`、`warn`、`pass`
- `minCount`：整次测试累计至少命中 N 次才触发，当前没有时间窗口
- `absence`：锚点出现后，在指定秒数内没有出现目标条件时触发缺失判定

设计要求：

- 能确定 Tag 时优先加 `tag=equals`，不要只用 message 关键字。
- 业务错误要同时限定模块 Tag、关键字和必要的级别，避免 SDK 普通日志误报。
- 正常流程用 `pass`；异常流程用 `warn` 或 `error`，不要把所有 Error 级别日志都当成业务失败。
- `regex` 需要测试正例、负例和边界值，例如 `0` 不应匹配 `0.1`，`-1` 不应匹配 `-10`。
- 多个 `pass` 规则表示多个成功信号都必须出现，适合 MAX/TopOn 这类闭环监控。

## 四、状态语义

当前有 5 种状态：

| 状态 | 计算规则 |
|---|---|
| `未启用` | `enabled=false` |
| `有问题` | 命中任意 `error`，或缺失判定超时 |
| `疑似` | 未命中 error，但命中任意 `warn` |
| `通过` | 存在 `pass` 规则，且所有 pass 规则都命中 |
| `监控中` | 没有明确错误、警告，或成功条件尚未全部满足 |

如果用例设置了 `requirePass=true`，成功条件尚未全部满足时会显示“疑似”，即使还没有命中 `warn`。这表示“尚未观察到完整成功信号”，不表示已经捕获到明确错误。

实际优先级为：

```text
未启用 > 有问题 > 疑似 > 通过 > 监控中
```

新一轮测试开始时，所有启用用例通常先显示“监控中”。纯异常监控用例在没有异常时会一直保持该状态；带多个 `pass` 规则的用例在成功信号全部出现后才变为“通过”。

以 `ie_adjust_revenue_fail` 为例：

```text
开始监控                    -> 疑似
仅出现部分价值回传成功日志   -> 疑似
四条价值回传成功日志全部出现 -> 通过
```

只有需要成功信号闭环的用例才设置 `requirePass=true`，不要把所有用例的初始状态都改成“疑似”。

## 五、新增用例流程

### 1. 先确认日志来源

- 在 `<unity-framework-src>`、`<unity-plugin-src>`、`<android-ad-library-src>` 和相关业务仓库中定位日志调用点。
- 在完整日志中确认实际 Tag、级别、消息格式、是否多行，以及同一关键字是否会正常重复出现。
- 只有源码可达且日志能稳定代表业务语义时，才进入内置用例。

### 2. 决定新增还是扩展

- 同一功能已有用例时，优先扩展现有用例，避免多个用例重复报告同一问题。
- 需要多个成功信号全部出现时，用一个用例配置多条 `pass` 规则。
- 只有在规则效果、排查对象或状态语义明显不同的时候，才新增用例。

### 3. 同步两份内置来源

先修改 `src/features/testcases/engine.ts`，再把同一用例同步到 `config/remote-config.json` 的 `testCases` section。检查 `id`、Tag、关键字、规则效果、分组和 scope 完全一致。

### 4. 用样例回放

至少验证：

- 正常日志命中预期规则。
- 异常日志命中预期规则。
- 相似但正常的日志不会命中。
- 多条命中日志都能在侧栏展示并定位。
- 测试用例页面不受普通日志 Tag 屏蔽影响。
- 切换应用、重置测试和重新启动后的状态符合预期。

### 5. 本地验证

```bash
node scripts/validate-config.mjs
pnpm exec tsc --noEmit
pnpm build
git diff --check
```

开发版 `pnpm tauri dev` 启动时默认读取仓库内的 `config/remote-config.json`，适合先验证新增用例；正式发布前再通过管理页生成、校验和发布远程配置。

## 六、发布和用户更新

- 调试版生成远程 JSON 时使用当前生效的内置与本地用例。
- 发布后，正式版用户会在远程配置缓存过期后的下一次启动自动拉取；当前缓存时间为 5 小时。
- 用户手动刷新配置可以立即拉取。
- 远程 `testCases` 整段替换内置定义；本地自定义用例仍保留，内置用例以远程最新定义为准。
- 发布前必须确认本地自定义用例是否应该进入公共内置配置，避免把个人临时规则发布给所有用户。
- 配置发布和应用版本发布是两条链路：仅修改远程 JSON 不需要发版；修改代码兜底或引擎能力才需要应用版本发布。

## 七、当前能力边界

- 测试 Tab 会先按目标应用 PID 过滤，`global=true` 不会读取系统进程日志。
- `minCount` 只统计整次测试累计次数，不支持“最近 N 秒内连续失败 M 次”。
- 缺失判定必须有稳定锚点；没有测试结束事件时，无法严谨判断“整个测试期间从未出现”。
- 多条 `pass` 规则只证明这些成功日志在本轮都出现过，不关联同一个广告位或同一个 `adPid`。
- 远程配置 section 整段覆盖，因此远程文件被删除某个内置用例后，正式版会以远程结果为准。

## 八、当前用例概览

当前代码兜底和本地远程配置均为 `47` 个用例。其中
`LevelPlay&TopOn 广告` 分组的 13 个用例仅对 `com.fruit.slicerush` 生效，详细执行顺序见
`levelplay-topon广告测试说明.md`。原有激励框架的广告用例排除 `com.fruit.slicerush`，其中包括：

- `ie_ad_fail`：广告插件确定性集成异常

广告分组新增 `unity_main_thread_violation`：Unity 主线程调用违规。

- 默认启用，`scope.global=true`，不设置应用排除项；对所有已选应用生效，包括使用 LevelPlay&TopOn 的项目和后续新增项目。分组仅用于方便广告测试时查找，不继承旧广告用例的应用排除项，也不限制异常必须来自广告模块。
- 匹配 Tag 为 `Unity` 且消息包含 `can only be called from the main thread` 的日志，大小写不敏感。不限定具体 Unity API、广告 SDK、调用阶段或日志级别，被框架 catch 后重新打印的异常也需要命中。
- 命中一次即显示“有问题”；没有命中时保持“监控中”，不因普通广告成功日志变为“通过”。它监控 Unity API 的线程调用违规，不把所有命中都归为广告加载失败。
