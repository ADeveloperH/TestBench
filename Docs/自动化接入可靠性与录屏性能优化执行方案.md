本文记录整改方向及实施状态，处理框架接入契约、玩法驱动、录制开销与 AI 接入耗时。**最新范围：只修改激励框架及通用提示词/检查，不修改游戏源码、项目配置或已安装工具；水果只作问题证据。当前采用普通提示词，不要求安装 skill，DeepSeek/Codex 共用同一正文。** 本文中的建议和验收目标不表示功能已经实现或真实运行通过。代码开始修改前，应重新核对工作区，不能将本次检查快照当成永远不变的事实。

## 1. 任务目标和工作范围

按阶段完成以下工作，每阶段同步相应文档并留下可复核结果：

1. 整理框架指南、标准契约、通用提示词，消除互相冲突、过期或只适用于某次工作的指令。
2. 修复单国家、单片段验证入口，让接入问题可以小范围重现。
3. 提供框架会话配置缓存及状态/决策耗时诊断，固化高频路径禁做完整资源调查的接入规则。游戏侧实际迁移由后续接入执行。
4. 收回按游戏帧观察/决策的通用驱动，区分下一输入条件与动作全部结束；把失败可达性、动态窗口、多阶段覆盖固化到契约和接入检查清单。
5. 框架补齐通用无进展诊断，缩短失败定位时间。
6. 优化 AI 接入工作流和预检，减少重复读取、编译和资源扫描。
7. 同步框架文档及 TestBench 索引，交付可由其他同事及不同 AI 重复执行的提示词入口。

仅框架可修改；不改游戏中的业务观察、适配器、文档、配置或旧工具。另一个 AI 已暂停框架写入，可继续完善；已有未提交改动保留。TestBench 只维护方案和索引，不引入本轮 Unity 实现。

不以大规模重写、换录屏库、换图引擎或新增一套自定义游戏图作为默认方案。全部按新游戏标准接入处理，不新增旧适配器兼容分支。

### 2.3 录屏现状及性能嫌疑

项目配置为 1080×1920、30fps、目标 10Mbps，声音开启。只读 ffprobe 检查上述成功视频：H.264、1080×1920、30fps、1810 帧、60.333 秒，视频实际平均码率约 7.79Mbps；AAC、48kHz、双声道。目标码率与实际平均码率不同，不能据此认定配置失效。

这些元数据不能证明视频内容没有停顿，也不能证明录制时 Editor 达到实时 30fps。

已发现有源码依据的高优先级性能嫌疑：

1. `ReadGameState()` 每次调用 `ValidateGame(game, true)`；后者重复查资源、解析关卡/分组 JSON、读取序列化对象并遍历水果结构。
2. `Resource<T>()` 使用 `AssetDatabase.FindAssets`，`Levels()/Groups()` 重复反序列化，`Catalog()/Guide()/ValidateFruit()` 重复创建 `SerializedObject`。这些工作不适合出现在频繁状态读取中。
3. `LoadGame`、`CaptureGameEvidence`、`AdvanceGame` 又重复调用同类校验，进一步放大开销。
4. 框架辅助 UI 步骤即使未找到按钮，也可能触发 GameView 聚焦、重绘和多帧探测，需测量空操作成本。
5. 监控窗口存在按节点搜索累计 trace 的路径，长循环下可能增加开销；网络上下文也会读取当前 trace。先量化，不直接重写。
6. 当前 Recorder 设置包含固定帧率和 `CapFrameRate=true`。本机 Recorder 4.0.3 源码存在限帧 sleep/忙等路径；这是待对照测量的行为，不可只看到 sleep 就关闭限帧。

以上为性能嫌疑，不是已确认的唯一瓶颈。方案实施须有前后对比数据。

推荐未来由 TestBench 下发任务、游戏内核心执行细粒度玩法和业务流程；TestBench 管理设备及采集生命周期。不要默认让每次游戏单步都经 adb/桌面进程往返，也不要默认把 C# 图引擎移植成 TypeScript/Rust。此建议不等于已确认的传输协议或已实现的运行时引擎。

本轮具体要求：

1. **分清语义与平台绑定。** 新增状态、进展、错误和结果契约不要求窗口聚焦、场景资产路径或 Editor 实例 ID；局次标识至少在运行会话中稳定且可关联，不用跨进程对象引用作证据。现有平台依赖列出后续替换点，不为预留做一次大迁移。
2. **隔离资源调查和运行事实。** AssetDatabase/SerializedObject 可服务 Editor 预检与开发；运行期状态读取不能以扫描工程源资产为前提。手机侧以后必须读取实际加载配置，不退回代码默认值。
3. **宏按阶段解释。** 现行启用条件为ENABLE_AUTOMATION；Editor专有API仍隔离。未来手机执行宿主需要经确认的会话/通信能力，不能把宏启用当作已实现手机自动化，并保证正式包移除ENABLE_AUTOMATION。不能简单全删 `UNITY_EDITOR`，也不能继续要求手机能力只存在于 Editor 目录。正式包排除项应覆盖代码、资源注册、命令入口和通信桥。
4. **输入与录制可替换。** Editor 焦点/Input System 和 Recorder 是当前实现。手机 Host 的输入与设备采集另做适配；设备实际分辨率、音频和编码能力需预检并记入报告，不能承诺 Editor 的 1080×1920/30fps 参数在所有手机原样成立。未来片段开始需等待采集就绪再加载关卡，结束需媒体收尾确认，避免远程时序丢头尾。
5. **关联信息统一，协议不抢先定死。** 后续任务协议至少覆盖版本/能力握手、任务/运行/国家/片段/局次/命令标识、错误码、取消和超时。启动、断线和重连不得重放提现、领奖等有副作用命令；恢复必须核对当前状态与已执行事实。实现前确认单一执行权归属，避免 TestBench 与游戏内核心同时推进同一流程。
6. **素材模式与真实测试分开。** 素材录制跳广告成功回调的策略不能无条件用于所有移动端测试；未来任务需显式声明模式及启用的测试替代能力，报告如实标记。素材成功不等于真实广告链路或完整线上业务已通过。
7. **AI 接入验收按平台声明。** 当前可交付“Editor 接入完成/待实测”，不能据此标记手机可用。未来同一游戏尽量共享玩法语义和证据映射，仅增加 Runtime 绑定/平台适配；若现有接入仅在 Editor，明确列出迁移工作，而不是要求 AI 默默重写另一套业务流程。

后续手机最小闭环：测试包能力握手 → TestBench 启动应用并确认就绪 → 下发单国家/单关卡任务 → 游戏执行正常玩法并返回本局证据 → TestBench 关联设备采集与报告。先验证成功、失败、超时/取消和断线不重复提交，再扩大到附加提现、多片段、多国家与现有监测联动。本轮不把该闭环列为已完成或必须立即实录的项目。

### 4.2 必须消除的歧义

逐项对照代码修正文档和提示词，不能只追加“注意”：

1. **不依赖预检缓存 ≠ 运行时禁止缓存。** 正式适配器必须独立初始化，但允许在本次会话内缓存实际配置、绑定和已验证对象；对象/配置变化后失效。每次状态读取不得全量扫描。
2. **实时核验 ≠ 每帧重验全部候选资源。** 预检验证静态支持范围；加载/替换时验证实际实例；高频状态读取只读轻量事实。
3. **InputIdle 的游戏动作语义与共享 Input.Busy 分开。** 飞刀仍在途和鼠标按键未释放不是同一事实；结果到达后的交接继续遵守标准基类契约。
4. **框架接受本次成功 ≠ 奖励按钮关闭或金币到账。** 前者由游戏交接证据表示，后者由框架结算流程推进，避免互等。
5. **有界结束 ≠ 必须伪造成功。** 策略无法收敛可明确失败，不自动修改游戏规则。
6. **信号 ≠ 全部状态。** 信号通知变化，快照提供可恢复事实，结果证据绑定本次局次。
7. **静态通过 ≠ 真实接入完成。** 成功/失败各自必须有实际验证；用户自行测试时列为待验收，不能代填 passed。
8. **“引导可选”是游戏确实没有引导时不实现特殊操作。** 不能将未知引导直接视为 NotRequired。
9. **素材成功/失败通用，但如何玩赢/玩输不通用。** 不能要求框架替每款游戏兜底玩法。
10. 包版本相同不代表契约未变或已发布；定位要核对实际解析包和契约。

从通用规范中删除“本轮只改框架”“水果正在由另一个 AI 重新接入”等临时工作限制；移入当次任务记录。历史验证保留为历史事实，不能与当前待办混写。校正过期游戏文档路径。

### 4.3 普通提示词和包定位

- 助手直接复制普通接入提示词，DeepSeek、Codex 等使用同一正文；不安装 skill、不生成或覆盖 AGENTS 规则。
- 权威任务正文在指南第7节，接口在标准游戏适配文档。只路由到当前包，不要求 AI 重新研究整个 SDK 或复制水果策略。
- 定位脚本留在框架包 `Automation/AI/resolve_framework.py`，命令带当前项目路径、依赖与契约指纹，支持 UPM/本地包及嵌套工程。Editor 只在 Library 保存本机定位提示。
- 包升级、同版本源码变化、项目/依赖变化时旧提示词明确失效，回助手刷新并重新复制。复制与定位不改游戏 Git 文件。
- 保留 Git 只读共享检查和 meta/忽略规则要求。旧游戏已安装文件不在本轮自动清理范围；新接入无需保留旧安装机制。

验收：从助手复制的指令能定位实际包、找到唯一指南并明确只实现游戏差异；文档中不存在已删除接口的可执行示例，不引用仅水果存在的程序集作为通用名称。

## 5. 修复最小验证入口

先完成该入口，使后续策略和性能验证不必启动全部国家/片段。

### 5.1 两种明确模式

1. 按现有片段 ID 运行：精确选择一个启用片段，保留该片段原有成功附加提现、收款和录屏设置。
2. 临时验证模式：明确给定片段类型和关卡，在内存中创建单片段计划，不改磁盘默认配置。成功片段是否带提现必须明确，默认不附加；不得意外继承别的片段的手工收款资料。

参数名可采用 `-country`、`-clipId`、`-flow`、`-level` 等，但须与实现、帮助和示例一致；这些是待实现契约，不是当前已经可用的命令。

### 5.2 参数与执行约束

- 片段 ID 不存在、停用、重复、参数缺值、非法整数、越界、重复/互斥参数都明确报错；非法值不得退回“全部/当前关”。
- 按 ID 和临时类型/关卡模式互斥，不暗中合并。
- 国家必须来自该游戏支持列表；缺省可选实际列表首项并报告，不硬编码 ID。
- 单片段入口必须只生成一个国家任务和一个录制片段，不能静默跑全计划。
- 即使只验证第 6 关失败，也正常执行所需首关引导/关卡准备；明确这部分耗时。
- 默认使用测试环境；清档/提现等依然遵循项目配置和用户授权，不为验证偷偷开启。
- 使用现有 Runner、预检、Recorder 和交付机制，不另造简化执行器；结束状态和退出码明确。
- 不启动第二个 Unity 打开同一项目；不让 CLI 示例在现有工作 Editor 中意外执行退出动作。区分独立命令行 Editor 和用户已打开的 Editor 入口。
- 本轮默认只做实现及非运行检查；原生 Editor、接口、清档和录制由用户自行测试，除非用户另行明确授权。

逻辑测试覆盖选择唯一性、非法参数、停用片段、项目配置不被写回、原计划对象不被改变、成功附加提现资料保留。先补当前新入口问题，不增加新的运行配置面板。

## 6. 录屏卡顿和状态读取优化

### 6.1 先建立可比较的基线

区分三个现象：Editor 实时运行慢、最终视频画面停顿、玩法策略长时间没有操作。最后一种不能当作编码性能问题。

在同一台机器、同一国家/关卡和相同录制参数下，按授权范围做以下对照；A/B 仅用于诊断，不保存覆盖项目设置：

| 对照 | 目的 |
| --- | --- |
| 正常游戏无自动化、无录制 | 游戏自身基础成本 |
| 自动化执行、无录制 | 适配器读取/策略/图引擎/界面成本 |
| 自动化录制、声音开启、监控窗口关闭 | 当前目标录制成本 |
| 相同条件打开监控窗口 | 判断可视化刷新增量 |
| 声音关闭的临时对照，仅在仍有必要时 | 判断音频采集增量，完成后恢复 |

先做单片段/短窗口，不用每组都跑六国。固定/记录实际布局或局次差异以说明对比可比性，不为测量擅自修改随机种子或玩法规则。长时间策略等待不计作性能优化收益。

建议低开销采集和阶段汇总：

- 使用 Stopwatch/现实单调时间的帧间隔 p50/p95/max、超过 33.3/66.7/100ms 的比例。
- 适配器状态读取调用次数、耗时与分配，完整资源检查次数。
- 决策、辅助 UI、图 Tick、监控刷新、日志 Flush 及 Recorder 相关成本。
- 录制开始/结束现实时间、游戏时间、实际记录帧数、视频时长及二者比值。
- 必要的 Profiler 标记、GC 分配和音视频同步情况。

不能仅用 Time.deltaTime 或 captureDeltaTime 证明现实帧率；Recorder 固定时间步会影响这些值。正常限帧等待与真正的计算/编码阻塞分开统计。采样应有上限，不每帧 Debug.Log 或写文件，不给诊断本身制造新卡顿。

### 6.2 游戏高频校验的接入要求（本轮不改游戏）

把验证分成三个层次：

1. 编辑态预检：检查实际序列化来源和所有支持资源候选，不启动游戏/请求。
2. 运行时初始化及变化检查：正式实例独立解析实际配置，关卡/局次、云控有效值、容器、刀具、引导绑定或对象池生成配置变化时重新核验相关部分。
3. 高频状态读取：读取已绑定对象和轻量事实；发现变化就失效/重建，不扫描整个 AssetDatabase 或反序列化全部配置。

具体要求：

- 从 `ReadGameState` 高频链移除重复 `FindAssets`、完整 JSON 解析、序列化反射和全部候选 Prefab 遍历。
- 保留来自正常 Scene/Prefab/运行对象的权威配置，不能为了缓存退回类默认值或猜 Resources 路径。
- 用会话内缓存及对象/配置代际区分有效性；对象池可能复用同一 InstanceID，不能只靠对象地址判定配置不变。
- 配置资产/原始云控值变化应能触发重新解析，不每帧计算整个资源的哈希。
- 可增加必要的只读访问器，ENABLE_AUTOMATION宏隔离；不为减少 SerializedObject 调用把游戏字段全部公开。
- 构造、Bind 和 ValidateEnvironment 不承担正式会话初始化；首次运行即使从未点预检也正常工作。
- Cleanup 清空会话缓存/监听；重启/域重载后的新实例不能依赖旧缓存。
- 不用捕获所有异常后返回默认快照的方式掩盖已失效配置。

验收：稳定运行阶段高频状态链中完整资源扫描/全量配置解析次数为 0；实际替换对象、配置变化和清理重建后会重新验证；错误配置仍然明确失败。

### 6.3 再处理测量证实的框架成本

- 框架无辅助按钮时的探测保持有界且轻量；不反复无条件 Focus/Repaint，不把空操作变成完整页面等待。
- 将“是否有可处理辅助 UI”的探测与“点击”适当分离，保留停留后重新核对、射线及正常输入，不直接调用业务按钮回调。
- 监控窗口只在实际显示且状态变化时增量刷新；若测量证实长 trace 搜索开销，维护当前/最新状态索引，不每次为每个节点重扫全历史。不能删除报告 trace 代替优化。
- 对长期不变的反射成员信息可缓存，例如录制帧数属性；不要把反射缓存当作首要大收益。
- 保留网络请求/响应正文和错误码。若 Flush 构成尖峰，做有界队列/批量落盘，阶段结束和失败前完整冲刷；不删除诊断，不从工作线程调用 Unity API。
- 不通过一次 Editor Update 执行多个有副作用节点来提速；不得破坏串行输入、现实请求等待及画面停留。

### 6.4 Recorder 和音频

先维持 1080×1920、30fps、目标 10Mbps 及当前声音设置。

只有前述优化后仍存在明确 Recorder 瓶颈，才比较限帧、音频和编码路径。结合实际安装的 Recorder 源码/接口核对固定帧率、音频采样、现实/游戏时钟，不直接改 PackageCache。

不要默认关闭 CapFrameRate、改可变帧率、禁用声音、降低分辨率/帧率/码率、改 timeScale 或全局 Fixed Timestep。若确需改变录制模式、输入时钟或编码库，先提交对照数据、行为差异和方案给用户确认。

前台和后台分别验证；Application.runInBackground 已开启不代表后台全速。后台输入隔离和 macOS 限速是独立问题，不能顺带保证已解决，也不在本轮引入原生按键屏蔽或系统焦点抢占。

验收提供前后表：同一测量范围的耗时/分配/长帧变化，以及 ffprobe、完整解码、运动片段首中尾和音画同步检查。30fps 元数据不是流畅度验收。没有真实测量时写“已消除源码重复工作，性能待用户测量”，不要声称提升若干倍。

## 7. 失败策略的接入映射要求（水果只读案例，本轮不改游戏）

### 7.1 先验证可控操作空间

沿真实输入链确认：点击坐标是控制方向，还是仅触发当前刀具发射。当前看起来点击主要负责触发发射，刀具横向位置由运动脚本控制；不得假设“点击左边就能往左射”。

核对刀具发射力、质量、物理步、移动相位/父变换、水果碰撞器、随机容器及波次/刀数规则。预测只用于选择操作时机，最终结果仍靠真实输入及业务证据。

优先修复并测量第 6 关第 4/5 波、容器 23 附近的原问题；再覆盖配置允许的其他布局。若不能复现相同随机布局，保留本次真实布局快照并说明，不能写原批次已复现。

### 7.2 策略要求

- 每次 AdvanceGame 只做有限采样/决策和至多一次正常输入；不得用同步 while 阻塞 Editor，也不在其中等待整局结束。
- 对当前局次、波次、容器和刀具维护必要策略状态；波次变化重建局部计划，同时保留整局预算。
- 不再以整局固定“3 次开隙”代表任意多波次支持能力。是否开隙、次数及后续策略需要结合当前水果/剩余刀数和误通关风险。
- 预测模型要考虑实际时延及运动，不只以当前速度线性外推就宣称必定 miss；尤其水果运动并非都由 Rigidbody 当前速度完整描述。
- 如果需要采样未来窗口，给出有界时间范围、计算预算和不确定度。预测分配/遍历不得成为新热点。
- 每次输入后等真实接受/飞行结束，观察是否命中、耗刀、换波或产生结果，再计划下一步，不盲目重复。
- 已发生目标失败立即交回框架核验；如果意外成功，明确报告实际结果相反，不能继续使用旧基线或悄悄再来一局。
- 对没有可行操作窗口的真实布局，在预算内明确失败并保存事实；不能持续采样直到整局大超时，也不能声称所有关卡天然可正常失败。

至少诊断：目标模式、局次、实际关卡、当前/总波次、容器、剩余刀数、剩余水果、本局派发/接受/命中/未命中计数、最后进展、窗口预测与本次决策原因。已有只读计数尽量复用，不记录每帧全量对象树。

### 7.3 不自动加入强制结果兜底

本轮默认不启用通过改刀数、改碰撞器、改难度、改随机种子、直接调用 ShowGameOver/胜利方法来产生目标画面的行为。

`ControlledOutcome` 现有空接口若没有完整且获确认的用途，应移除对应空实现/示例/“已支持”宣称，而不是让后续 AI 自行决定调用方式。先说明清理范围再同步契约摘要。

若真实正常操作无法稳定覆盖目标布局，向用户提交具体证据及两种选择：继续完善正常策略；或单独设计“预设录制条件”模式。后者须在加载前显式配置、仍走原有业务结果链、报告标明差异，并设计恢复，不允许运行失败后静默切换。

## 8. 框架通用进展和错误诊断

最小扩展现有标准基类，不另建执行器。先写字段/生命周期契约，再实现并测试；接口名可按现有风格调整。

建议游戏提供本次上下文范围内单调递增的进展序号及最近进展原因，例如输入被真实接受、波次推进、目标完成或结果产生。仅派发输入、重复决策、循环次数、时间流逝、周期性位置变化和日志输出不算业务进展。

框架维护：

- 最近有效进展、无进展持续时间、已有总次数/总时长。
- 检测作用覆盖不允许再次输入的等待状态；不能只在 AdvanceGame 内计时，否则 Ready=false 时可能永远不检查。
- 画面/玩法进展默认按游戏时间，接口按现实时间；计时明确，不用时间混合放宽无限等待。
- 无进展预算建议先以 15 秒游戏时间评估，结合游戏实际运动周期；现有 300 秒/1000 步总上限继续保留，不因为不断进展就取消总上限。超过该预算确有合理需求时先说明再调整。
- 引导、成功、失败开始/准备/加载/清理时正确重置；旧上下文与回退进展拒绝。
- 结果在辅助步骤、输入等待或波次切换期间到达，仍及时交回核验/结算，不等待结果弹框消失。

错误分类可采用 `gameplay_no_progress`、`input_not_accepted`、`unexpected_outcome`、`result_evidence_invalid`、`gameplay_strategy_exhausted`、`unsupported_gameplay_configuration`、`ui_blocked` 等稳定代码，同时保留原异常、国家、片段、关卡、图/节点/调用路径、实际状态及网络关联。

结果相反、旧局结果、未知配置、接口失败不可自动重新提交升级/领奖/提现；玩法备用策略也不能吞掉这些错误。

## 9. 信号接口的处理范围

本轮不将“大范围信号重构”作为修复失败/卡顿的前置条件。先复用游戏现有事件与只读事实，只在能减少重复和侵入时增加小型观察对象。

若要提出信号接口，必须先明确：订阅之前事件已发生如何恢复；加载/新局标识；输入接受与释放；结果和交接证据；重复/迟到/跨局事件；对象池复用；清理/重建；错误传播及线程边界。

推荐“事件通知 + 当前快照 + 保留本次结果证据”。仅事件总线不能取代 RunId/ResultLevel、快照恢复和证据验证。自然业务点仍需准确选取，不能宣称改成信号后不再依赖调用时机。

为第一款游戏新增小型观察封装可以作为局部整理；新增所有游戏必须实现的大接口，先给出收益、最小契约和用户确认点，再实施。

## 10. AI 接入耗时优化

用户反馈一次新接入约 30 分钟。先记录耗时分布，不能预设都花在模型推理，也不承诺所有游戏固定几分钟完成。

### 10.1 记录一次接入的阶段成本

记录包定位、框架契约读取、游戏调查、方案确认、代码修改、Unity 导入/编译、静态预检、错误返工、真实录制及结果整理的起止时间和次数。用户等待和未获授权的实测单列；不要读取与任务无关的私有聊天或上传源码做统计。

至少能回答：是否反复读同一文档/源码，是否频繁小改触发编译，是否各国重复全量扫描，是否每次验证先走全部首关/跳关，是否策略写完后才首次尝试失败。

### 10.2 最小阅读和实现路径

通用提示词按顺序引导：

1. 定位实际包并读取短接入入口、标准基类契约和相关版本差异。
2. 有针对性搜索游戏入口、权威关卡、加载、正常输入、引导、结果/交接与配置实际绑定。
3. 在游戏现有接入记录填写来源和支持范围；无法确定的业务点先向用户确认，继续处理其他独立项。
4. 实现一个标准适配器、必要的 Editor 程序集和最小任务配置；仅在业务事件不足时补ENABLE_AUTOMATION宏观察点。
5. 集中完成一组相关修改后编译、预检；根据具体错误局部修复，变化后不得沿用旧报告。
6. 先验收单国家单成功/失败，再成功附加提现，最后扩国家/关卡。

不要默认读取整个 SDK、所有历史文档、所有国家长日志、全部水果源码或所有 Assets。读取少不等于只读默认字段：实际 Scene/Prefab/云控覆盖的来源核对仍是必须项。

提供一个维护在标准文档中的最小代码骨架和交付清单即可，不新增第二套生成框架。未实现方法明确失败；不自动生成空成功。手工填写 Id/入口/程序集等可由助手做确定性检查；复杂玩法策略仍由接入者分析，不能靠模板假装完成。

### 10.3 拆分预检 减少重复工作

当前标准契约检查和每国 ValidateDocument 都可能执行完整 `ValidateEnvironment`。调整为同一轮预检内：

- 公共检查：实际入口、程序集注册、标准契约、游戏静态支持范围与资源完整性，按相同游戏/配置执行一次。
- 各国检查：国家可用性、有效支付渠道/字段、地区覆盖、计划组合及环境限制分别执行。
- 运行前保留必要的最新有效性检查；配置变化则重新检查。

复用范围限于该轮检查上下文。若国家确实会改变游戏资源/策略，则按该有效配置分组检查，不能无条件跳过。正式 Host 不依赖该轮预检实例；不把带副作用的 provider 长期保活来缓存预检结果。

同一轮发现重复创建适配器、重复打开场景或全量解析资源时减少重复；保留原来已打开场景和用户改动。Unity API 留在主线程，不用并发调用 AssetDatabase/SceneManager 提速。

禁止对修改过的源码偷偷沿用旧 DLL 作“当前编译通过”。若用依赖快照做局部编译，报告清楚范围；不要求每次接入都先搭一套临时编译器/平台替身。优先使用现有项目可用的检查路径。

### 10.4 分层完成状态

接入报告区分：当前契约已定位、适配器编译通过、静态接入检查通过、成功实测通过、失败实测通过、附加提现实测通过、多国家/媒体验收。尽量在现有报告中表达，不为此先做新面板。

用户自行实测时，交付到“待实测”并提供准确的单片段操作，不假装自动完成了真实验收。不让接入 AI 每次都从首关跑六国才能交付一个编译修复。

提速目标是减少可测量的重复成本和返工，不删掉关键核验，也不强行要求半小时缩到固定分钟数。简单游戏与复杂物理游戏分别记录，稳定性优先。

每阶段完成后先做相关检查再继续，不把大量改动攒到最后一起编译。若 C 优化影响策略时延，D 必须基于优化后实际节奏验证，不能沿用旧物理参数猜测。

最低回归范围：

- 标准成功/失败/贯穿玩法的引导；输入在途与辅助 UI 内异步到达结果；旧局结果拒绝。
- 首次运行未点预检、同会话 Bind、Cleanup、新实例、对象/配置替换、对象池复用。
- 无进展/总预算/相反结果；不执行重复输入或重复业务提交。
- 第 6 关失败原问题、多波次/不同实际布局、成功路径未退化、失败后恢复并继续下一片段。
- 成功附加提现足/不足、真实拒绝、停录后恢复；已有业务不得因本次提速被绕过。
- 包定位/旧提示词拒绝、C#/Python 摘要一致、复制只读、共享文件/.gitignore/meta。
- 文档/提示词路径和示例；当前源码编译；相关图/配置测试。

用户实际验证建议：先单次第 6 关失败，确认真实失败弹框和视频，再重复至少 3 次覆盖实际不同布局；再成功附加提现与失败相邻的短计划。此次数是最小抽样，不代表全部关卡/随机布局均被证明支持。没有用户授权不自行执行这些真实运行。

性能报告分 Editor 实时耗时、最终视频质量、后台表现；测试数据、窗口状态、参数和测量范围写清。录制文件不复制到 TestBench，不修改旧报告，不为展示成功移动 interrupted 视频进交付目录。
