# TestBench 界面开发规范

> 这份规范用于后续通过 DeepSeek Harness 或其他开发代理迭代界面。开始任何 UI 需求前，先阅读本文件以及 `src/App.css` 中已有的组件样式；优先复用既有组件与变量，不重做已有交互。

## 设计目标

TestBench 是面向测试与开发的桌面调试工作台。界面应当像专业日志/设备工具：

- **深色、高密度、可长期使用**：默认深色，弱化大面积装饰，信息密度高但层级明确。
- **任务优先**：实时日志和当前设备始终是主角；设置、整理、低频偏好不干扰测试会话。
- **状态清楚**：运行、通过、警告、错误、危险操作应通过颜色和文案共同表达，不能只靠颜色。
- **保留浅色主题**：所有新增界面必须同时适配 `body.light`。

## 视觉基础

颜色和字体统一由 `src/App.css` 顶部的变量提供。新增样式优先使用：

| 用途 | 变量 |
|---|---|
| 页面背景 | `--bg` |
| 工具栏/面板背景 | `--bg-toolbar` |
| 输入框、次级按钮背景 | `--bg-input` |
| 分割线、边框 | `--border` |
| 主文字 / 次文字 | `--text` / `--text-dim` |
| 悬停背景 | `--hover` |
| 主操作与选中状态 | `--accent` |
| 成功状态 | `--ok` |
| 日志和技术信息字体 | `--mono` |

推荐的视觉节奏：

- 普通控件高度为 `32px`；紧凑图标按钮为 `26–32px`。
- 圆角以 `6px` 为主，面板/弹窗可用 `8–10px`；不使用过大的圆角或胶囊按钮。
- 面板采用细边框和轻微深浅差，而不是厚阴影或大量卡片。
- 危险状态使用红色，警告使用橙黄，成功使用绿色，信息使用蓝色。日志级别颜色保持现有规则。

## 页面与功能归属

### 实时日志（默认页）

日志页只能有 **两行顶部功能区**：

1. **会话与高频操作**：设备选择/刷新、开始或停止采集、暂停、清空，以及导出、WiFi、工具、测试用例、更多。
2. **筛选操作**：搜索、输入框内的正则 `.*` 切换、Tag、应用、日志级别、已保存过滤器和“保存筛选”。

规则：

- 不要在日志页重新加入第三行工具栏。
- 删除、重命名、排序、编辑筛选器放在 **设置 → 过滤器**；日志页仅用于应用和保存当前筛选。
- 字号、主题、设置入口放在 **更多** 菜单。
- 右侧测试用例栏用于实时状态与定位日志；复杂规则编辑在设置页的“测试用例”标签中完成。
- 选中日志时使用底部详情区，不新增重复的详情卡片。

### 工具页

工具页用于影响当前连接设备或应用的即时操作：应用后门、重启、清数据、卸载、截图、安装 APK、投屏、录屏、设备信息、Activity、Alarm、性能等。

- 必须全宽显示，不能限制在居中的窄栏。
- 清除数据、卸载等危险动作必须保留现有确认步骤。
- 应用选择必须使用可搜索的 `Select`，并尽量完整展示“应用名 + 包名”。

### 设置页

设置页用于持久化配置：应用清单、搜索/Tag 常用项和历史、已保存过滤器、测试用例、帮助、配置导入导出与调试日志。

- 必须全宽显示。
- 不把设备即时操作或日志采集操作移进设置。
- 配置管理可使用列表、标签页和编辑区；避免不必要的仪表盘式指标卡。

## 组件约定

### 选择框与历史输入

- **只能使用** `src/components/Select.tsx`，不要恢复原生 `<select>`。该组件会将菜单渲染到 `body`，避免被两行工具栏、滚动容器或 Tauri WebView 裁切。
- `Select` 的箭头是 CSS 三角形；不要使用 `▾`、`▼` 等文字字符替代。文字靠左、箭头靠右，展开时向上翻转。
- 搜索与 Tag 输入使用 `HistoryInput.tsx`。它的常用/历史菜单同样是窗口级浮层；不要把菜单重新嵌回工具栏。
- 从历史记录“设为常用”时使用现有描述弹窗，而不是直接写入。

### 弹窗与浮层

- 需要用户填写说明、名称或确认复杂操作时，优先用居中的遮罩弹窗；点击遮罩空白处或 Esc 可取消。
- 小型上下文操作（例如更多菜单）可使用锚定浮层。
- 弹窗和下拉层必须高于日志、侧栏和工具栏；新增浮层应避免被任何 `overflow` 容器裁切。
- 保存筛选使用“保存当前筛选”弹窗；输入内容是对该筛选组合的描述/名称。

### 图标与按钮

- 顶部高频动作使用 `App.tsx` 中的 `ToolbarIcon`（内联 SVG）加简短文字；新增图标应补到该组件，线宽与现有图标一致。
- 不使用 emoji 代替新增的工具栏图标。
- 普通次级按钮保持文字；危险按钮使用 `danger` 样式。
- 禁用状态必须保持可辨认的低对比度，并保留不可点击行为。

### 测试用例

- 新建用例保持现有流程：选择分组后直接创建默认用例，并在列表内打开编辑器。
- 分组展开、用例预览展开使用 CSS 三角形，不使用文字三角形；尺寸和位置参考 `tc-group-arrow`、`tc-item-toggle`。
- 不要在未确认需求的情况下改变用例编辑器、规则树、缺失判定或内置用例逻辑。

## 实现边界

1. 先确认现有功能所在页面，再决定是否只改样式或调整入口；不能为了界面简洁删除已实现能力。
2. 高风险操作、配置导入导出、日志过滤、PID 解析、测试规则逻辑属于功能逻辑；UI 改动不能改变其语义。
3. 新增页面优先复用 `manage-page`、`manage-section`、`Select`、`HistoryInput`、`Tip` 和既有主题变量。
4. 新增样式应集中到 `src/App.css` 并同时写出深色/浅色规则；不要在 JSX 中散落大量内联颜色。
5. 当窄窗口空间不够时，日志顶部两行可横向滚动，但下拉菜单和弹窗必须保持可见。

## 交付检查

每次 UI 修改后至少执行：

```bash
pnpm build
git diff --check
```

提交前检查：

- 日志页顶部没有超过两行的常驻功能区。
- 工具页和设置页为全宽工作区。
- 选择框、历史菜单、弹窗不会被工具栏或滚动容器裁切。
- 深色与浅色主题均使用正确的变量和边框层级。
- 没有删除或伪造现有功能。
