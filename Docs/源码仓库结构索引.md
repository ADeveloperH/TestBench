## 一、两套仓库的角色分工

### 1. IncentiveEngine

- 这是完整的 Unity 激励框架工程，包含运行时业务代码、配置、样例和编辑器工具。
- 后续如果要判断一条业务日志属于什么模块、某个功能的主流程在哪里、某个测试用例应该挂到哪个模块，优先查这里。
- 对 TestBench 来说，这个仓库最关键的是：
  - 统一日志格式
  - 业务模块划分
  - 功能 TAG 的定义位置
  - 激励框架功能主流程

### 2. UnityPlugin

- 这是插件与原生能力的源仓库，实际要按三层来理解：
  - `UnityPlugin/UnityPlugin/*`：Unity 侧插件封装、C# API、Unity 与 Android 的桥接层
  - `UnityPlugin/AndroidLibrary/*`：直接给 Unity 工程消费的 Android Library
  - `UnityPlugin/SDKMaskShell/zeus/repos/middleground/*`：Android Library 继续依赖的内部 Android SDK 源码池
- 后续如果一条日志来自插件层，或者需要判断 Unity 是怎么调到 Android 的，优先查这里。

## 二、推荐的查找顺序

遇到任意一条日志、模块名、测试点时，建议按这个顺序查：

1. 先看 IncentiveEngine 的业务模块代码，确认是否为框架自身逻辑。
2. 如果是 Unity 插件能力，再看 `UnityPlugin/UnityPlugin/<plugin>` 的 C# 封装层。
3. 如果 C# 层使用了 `AndroidJavaClass` / `AndroidJavaObject`，继续顺着类名查 `AndroidLibrary`。
4. 如果 `AndroidLibrary` 本身还依赖内部 SDK，再继续顺着 `build.gradle` 查到 `SDKMaskShell/zeus/repos/middleground`。
5. 如果 Android 类名或依赖 SDK 在当前仓库中都找不到，再标记为“外部依赖或未提供源码”。

## 四、IncentiveEngine 的日志约定

### 1. 统一日志入口

文件：

- `Assets/Runtime/IncentiveEngine/Scripts/Common/Log/LogUtils.cs`
- `Assets/Runtime/IncentiveEngine/Scripts/Common/Log/README.md`

当前已确认的规则：

- 普通日志格式：`[TAG]: message`
- 例如：`[Withdraw]: 提现档位拉取失败: ...`
- 未传 tag 时，直接输出 message
- 广告专用日志通过 `IAALog(string message)` 输出，格式为：
  - `[IAA] message`
- 所有 `LogUtils` 输出都受 `ENABLE_LOG` 编译宏控制
- 这意味着：
  - 业务逻辑是否写了日志，要看源码
  - 日志在测试包里能否出现，还取决于 `ENABLE_LOG` 是否开启

### 2. 对 TestBench 的意义

- logcat 外层 tag 往往还是 `Unity`
- 真正区分模块的关键，通常在 message 里的 `[TAG]`
- 所以后续整理“业务 Tag”时，核心来源应该是：
  - `private const string TAG = "..."` 这类定义
  - `LogUtils.Info/Warning/Error/Exception` 的调用点
- 广告日志是一类特殊情况：
  - 既可能出现普通业务 TAG
  - 也可能出现 `[IAA]` 这类前缀

### 3. SDKMaskShell / middleground

这是很关键但容易漏掉的一层：

- 路径：`/Users/shareit/UnityPlugin/SDKMaskShell/zeus/repos/middleground`
- 这里不是单个 SDK，而是一组内部 Android SDK 仓库池
- 目录里当前可见的仓库很多，例如：
  - `sdkbasecore`
  - `SDKBaseUser`
  - `SDKBeyla`
  - `SDKConfig`

  - `SDKStarter`
  - `SDKWidget`

  - `SDKLocation`

这一层对后续工作的意义：

- 某些 Android 日志并不直接写在 `AndroidLibrary` 仓库里，而是来自这些内部 SDK
- 后续做 tag 归类、噪音识别、测试用例时，遇到 `Android.*` 日志如果在 `AndroidLibrary` 里只找到一层调用，很可能还要继续追到这里

但这里要特别注意一个边界：

- `middleground` 里“存在的仓库”不等于“当前项目一定实际用到了”
- 不能因为目录里有某个 SDK，就直接把它当成当前游戏或当前 AndroidLibrary 已接入的依赖
- 是否真的使用，必须再结合下面几类证据确认：
  - `UnityPlugin/AndroidLibrary/*/*/build.gradle`
  - `UnityPlugin/SDKMaskShell/unity_plugin_java_sdk_dependencies.md`
  - `UnityPlugin/Config/repos_sdk.csv`

这三份信息的判断方式不同：

- `build.gradle`
  - 最接近“当前 AndroidLibrary 真实声明了什么依赖”
- `unity_plugin_java_sdk_dependencies.md`
  - 适合快速看“某个 AndroidLibrary 大概率会牵到哪些内部 SDK”
- `repos_sdk.csv`
  - 更像 SDK 源仓库清单和发布参与清单
  - 其中 `publish=yes` 代表它参与 SDK 发布列表，不代表当前游戏一定接入了它

### 2. AndroidAdManager 入口

当前已定位文件：

当前要点：

  - `Manager`
- 会输出类似：
  - `AndroidAdManager init skip topon: ...`
  - `AndroidAdManager init skip max: ...`

  - `AndroidAdManager ... mediation is required`
  - `AndroidAdManager ... unsupported mediation`

### 3. 广告原生日志入口

当前已确认主要有这几类：

- `AggLog`
  - 文件：`ads/AdAggregation/.../AggLog.kt`
  - 默认聚合 tag：`ad_aggregation`
- `MLog`
  - 文件：`ads/all_adapter_max/MaxAdxLayer/.../MLog.kt`

- `H5Log`
  - 文件：`ads/AdH5SDK/.../H5Log.kt`

- `HADLog`

说明：

- 这些日志工具大多优先走 `com.ushareit.base.core.log.Logger`
- 如果不开启统一 Logger，也会直接回退到 `android.util.Log`
- 因此完整日志里看到的 tag，既可能是固定默认 tag，也可能是业务类主动传入的 tag

### 4. 当前已知的广告日志线索

后续遇到这些 tag，可以直接先查对应模块：

- `Manager`
  - Android 统一广告入口
- `ad_aggregation`
  - 聚合层基础日志
- `[MaxAdx]`
  - ADX 层日志
- `H5AdSDK`
  - H5 SDK 日志
- `H5AdLog`
  - H5 广告辅助日志

此外，部分广告模块会把类名或业务 tag 直接透传给 `AggLog(tag, msg)`，所以还可能出现更细的 tag，例如：

- `ToponAdService`
- 各具体广告类型类名
- 自定义字符串 tag

这类细粒度 tag 后续要结合完整日志再确认是否真实会出现在宿主项目里。

### 5. 广告变体与接入边界

当前看到一个需要长期注意的边界：

- `UnityPlugin/adplugin` 的 Unity 桥接代码当前写的是：
  - `com.foundation.unity.androidad.AndroidAdManager`
- `AndroidADLibrary` 当前实际源码里的包名是：
  - `com.ushareit.unity.androidad.AndroidAdManager`

这可能意味着几种情况：

- Unity 插件代码比 Android 源码旧
- Android 侧做过包名迁移，但 Unity 桥接还没同步
- 宿主项目实际接入的是另一个产物或重打包版本

所以后续如果遇到广告功能异常，除了看日志本身，还需要优先确认“当前接入产物”和“当前源码分支”是否一致。

### 6. 日志 Hook 机制

仓库中还有一套日志拦截机制：

- 文件：`LOG_HOOK_README.md`
- 作用：
  - 通过 ASM 字节码插桩拦截 `android.util.Log`
  - 自动记录到 `LogCollector`
  - 不改变原始 `Log.*` 输出

这说明：

- 在广告 demo / 调试工程里，某些 `Log.*` 可能被额外采集到日志查看器
- 但对宿主游戏来说，真正进入 logcat 的 tag 仍然要以原始 `Log.*` / `Logger.*` 输出为准

## 十、后续整理 Tag / 测试用例时的使用建议

### 1. 提炼业务 Tag

优先来源：

- `IncentiveEngine` 中的 `private const string TAG = "..."`
- `LogUtils.Info/Warning/Error/Exception` 调用点
- `ADLog`、插件层 `Logger`、原生 `TAG`
- 完整运行日志中实际出现的 message 前缀

不要一开始就直接把所有代码里的 Tag 都做成内置项，因为：

- 有些只在开发/编辑器环境出现
- 有些是低频或内部实现细节
- 有些更适合做测试用例规则，而不是用户直接筛选项

### 2. 设计测试用例

建议按三层来源组合：

- 激励框架业务日志
- Unity 插件层日志
- Android 原生 SDK 日志

同一个问题点，有时会在两层甚至三层留下线索：

- 业务层提示“初始化失败”
- Unity 插件层提示“桥接未初始化”
- Android 原生层提示具体 SDK 错误

### 3. 查问题时的快速入口

如果日志里看到：

- `[Withdraw]`、`[TaskManager]`、`[UserDataManager]`
  - 先查 IncentiveEngine 的 `Feature`
- `[IAA]` 或 `广告日志:`
  - 先查 IncentiveEngine `Common/IAA` 与 `UnityPlugin/adplugin`
- `ConfigPlugin ...`
  - 先查 `UnityPlugin/configplugin`
- `AndroidCloudConfigManager`
  - 先查 `AndroidLibrary/androidconfiglibrary`
- `PromotionManager ...`
  - 先查 `UnityPlugin/promotionplugin`
- `AndroidPromotion`
  - 先查 `AndroidLibrary/androidpromotionlibrary`
- `Push`
  - 先查 `AndroidLibrary/androidpushlibrary`
