## 1. 背景与目标

IncentiveEngine 是公司通用的 Unity 激励框架（当前 npm 包 `com.foundation.unity.common.incentive`，20.0.5），接入方游戏（示例：Lucky Fruit Quest 切水果游戏）在其上构建玩法。目前存在两个诉求：

1. **素材录制**：自动操作游戏、录制高质量视频素材，交付素材同学使用（投放/宣传）
2. **自动化测试**：在真实手机上自动执行测试用例，覆盖激励框架核心流程（提现/任务/广告等），失败可归因

两个诉求共享同一套底层能力：**自动操作游戏 + 录制/留证 + 编排执行**。因此设计一套统一的自动化系统，分阶段落地。

### 1.1 最新需求确认（2026-11-05）

- **操作步骤提前定义，后续全部由 AI 维护编排文件与必要的能力代码**（2026-11-09 更新，见 §1.28）；执行器按照校验后的预设顺序和条件执行。AI 维护不等同于运行时让模型临时决策。
- **启动也纳入自动化流程**：长期目标是一次点击后，尽可能自动完成环境检查、启动应用、等待初始化、准备状态、操作、录制、输出和清理。
- **可视化调整为只读流程与执行状态查看**（2026-11-09 更新）：保留主图/子流程、节点详情和执行路径，取消人工添加、连线及属性编辑的产品目标。已实现的编辑器为迁移前状态，见 §1.25；早期行为树式交互需求为历史记录。
- 第一版优先在 Unity Editor 落地。Editor 启动指进入 Play Mode；真机应用启动由后续 TestBench 外部执行器负责。
- 共享动作、状态、等待和证据等基础能力；素材与测试分别定义成功条件及失败处理策略。

### 1.2 分阶段交付与验收边界

1. **编排定义与查看工具**：由 AI 维护可校验、可版本管理的场景及子流程；使用者选择场景、调整受支持的任务参数、查看流程并运行。新建/编辑不再要求在画布完成；已有人工编辑能力按 §1.28 迁移。
2. **Editor 最小执行闭环**：在工具中点击运行，自动进入 Play Mode、等待初始化、记录当前游戏起点、执行预设玩法操作、录制并输出文件；支持停止、超时、基础结果校验及失败清理。
3. **扩展与真机接入**：根据实际场景增加国家矩阵、批量任务、片段复用，再接入 TestBench 的应用启动、真机操作、录屏和测试判定。

首条场景的具体关卡、操作节奏、录制起止与成功条件在实施时细化。简化版界面和运行闭环分别验收，不以界面完成、JSON 可保存或静态检查通过代替真实执行验收。

**扩展如何发生**：

- 新增已有状态的分支：在相应功能子图增加判断/等待/校验并连线，通常只改编排。状态或动作尚不存在时，需要先由适配器暴露，不能只画一个节点就获得能力。
- 新增一个业务模块：先用现有动作节点与子图调用组合，主图只增加一个功能调用。已有通用控制节点不够表达新的执行语义时，才扩充节点类型；当前类型由 `FlowKinds`、`FlowValidator`、`FlowEngine` 和编辑器共同维护，尚非动态节点插件系统。
- 接入不同 Unity 游戏：保留通用编排器，为新游戏实现启动就绪、新手引导、单次玩法操作、关卡完成等动作/状态，再编排对应流程。切水果的瞄准算法不能直接用于消除、合成等玩法。当前 `IFlowGameAdapter` 可注册多个游戏，一次场景选择一个游戏适配器，同时组合独立 `IFlowFrameworkProvider`；提现等框架自动化已抽回框架，见 §1.17。
- 防止图继续膨胀：主图表达测试目标，功能图表达业务步骤，连续瞄准/拖动等按帧策略留给动作实现。优先完善动作参数/返回值类型、状态描述与前置条件，减少手填字符串；当前已有框架模板与游戏库组合；任意共享库和版本依赖按多场景实际需求再引入。

**当前文件为什么还不能直接交给 TestBench 执行**：

1. 当前框架 `material_capture.json` 与游戏子流程库组合为 schema 2 执行快照，图、节点 ID、连线、参数和子图可复用；旧 `game_smoke.json` 已删除。TestBench 当前并无该格式的解析器、图执行器或导入入口。现有“导入测试用例”接收日志规则配置，不能用来导入该图。
2. `FlowModel` 与 `FlowEngine` 位于仅 Editor 编译的程序集；模型/存储同文件还依赖 UnityEditor。图执行主体不依赖 GraphView，但不能原样放进手机包或 TypeScript/Rust 中使用。
3. `IFlowHost` 的 Invoke/TryRead/Record 为同步进程内接口；远端执行需要请求关联、提交确认、进行中/完成/失败、超时和取消语义，不能简单用网络调用替换后就视为等价。当前长动作以“发起动作 + 等待状态”表达，未来可以保留这种图形用法，底层协议仍需完善。
4. 启动由 `FlowEditorRunner` 在图运行前进入 Play Mode，`launch` 节点只是确认；`Scene` 是 Unity 资源路径。真机需要包名/启动 Activity 等端绑定，以及真正的安装/启动/连接生命周期，不能直接解释 Unity 场景路径。
5. 当前框架业务提供者使用 `UnityEditor.SerializedObject`，共享输入会话使用 Game View 焦点和 Editor 专用 Mouse 驱动；`AutomationSessionDriver` 受 `UNITY_EDITOR && ENABLE_AUTOMATION` 限制，Android TEST 包没有这些能力。必须提供可编译运行的动作/状态桥与设备输入实现。高频瞄准策略宜在游戏内运行，通过正常输入链操作，不宜每一帧由 adb 往返控制。
6. Recorder 属于 Editor。TestBench 已有应用启动/重启、adb、日志和 scrcpy 录屏，但录屏当前会弹出保存对话框，未按自动化任务无交互管理，也未承接图中的分辨率/帧率或片段时钟。真机尺寸/帧率受设备与编码器限制，需检查支持情况并报告实际参数，不能保证沿用 Editor 的目标尺寸/帧率（当前默认 1080×1920 / 30fps）。
7. 现有报告中的证据路径是本机绝对路径，运行时间也不是统一跨端事件协议；传给 TestBench 展示还需要产物清单/相对路径、运行/节点/调用实例标识及时间基准。报告导入展示与控制设备执行是两项不同能力，目前均未接入。

**建议下一阶段的最小契约（待确认实施）**：

- 保留一份业务流程定义作为编辑源，导出时检查版本、图结构及所需动作/状态；同一文件内子图可随包携带。已有 schema 2 是起点，尚未冻结成最终跨端协议；需要不兼容调整时显式迁移，不能让两端各自猜测。
- 将业务流程与执行端绑定分开：流程保留动作、条件、调用与录制意图；Editor 绑定启动场景和 Recorder，Android 绑定包名/设备及设备采集能力。端绑定是运行基础信息，不恢复已移除的多运行配置选择器。
- 动作/状态提供能力 ID、参数/返回值类型及能力版本；执行前核对缺失/不兼容能力。共享的是能力契约和业务图，具体平台实现允许不同；不支持时明确拒绝，不静默绕过节点。
- 推荐由 TestBench 管理任务生命周期和图执行，手机 TEST 包中的框架桥执行语义动作/提供状态，adb/scrcpy 承担设备与采集能力。Editor 继续使用本地 Host；两端执行器需用相同契约样例验证分支、未知条件、子图局部数据、有限重复、失败与取消语义一致，避免双端漂移。
- 远程请求必须关联本次运行/节点/请求，动作超时或断线不能盲目重发有副作用的操作；取消和失败仍由执行器保证停录与清理。完成业务动作与“命令收到”分开记录。
- TestBench 的日志规则继续负责判定观察到的日志，自动化图负责执行操作。接入时以本次运行/步骤的日志边界关联结果；不得修改现有作用域、规则树、缺失判定或恢复配置语义，也不能将旧成功日志算成本次通过。

**建议推进顺序**：先整理最小跨端契约、抽出可在 TEST 包运行的能力层；再以 Fortuna 的“启动 → 等待就绪 → 页面操作/分支 → 录屏 → 校验/停止”完成 TestBench 真机小闭环；随后扩整关玩法，并选第二种玩法验证适配边界。TestBench 首期提供导入、选择设备、运行/停止、结果和证据查看即可，完整第二套图编辑器、跨场景库和批量矩阵不作为前置条件。当前主图与子图无需因接入而重新手工编排，但具体动作实现和部分端字段需要迁移。

**游戏现在如何接入 Editor**：

1. 接入框架及所需编辑器依赖，启用 `ENABLE_AUTOMATION`，提供实际正常启动场景；不需要实现节点编辑器、图执行器或 Recorder。
2. 在游戏 Editor 程序集中实现现有 `IFlowGameAdapter`：唯一 `Id`/展示 `Name`、场景使用的 `Actions`、显式 `StateKeys`、`TryRead` 状态读取、`Bind(FlowInputSession)` 和 `Cleanup`；`ValidateEnvironment` 为可选环境检查。动作和状态仅注册 `game.*`。图的 `Adapter` 绑定该 ID，Editor TypeCache 自动发现公开实现；框架 `framework.*` 提供者同时注册。输入使用 Bind 注入的共享会话，最终由宿主释放，不再为每个提供者创建输入设备。
3. 仅实现场景需要的游戏能力：例如游戏就绪、引导当前步骤、一次合法玩法输入、该输入是否完成、真实通关/失败结果。不同玩法可暴露不同动作，不要求所有游戏实现发刀、波次或快速通关。复杂连续操作可封装为一个动作，业务阶段与选择仍在图中表达。
4. 若现有公开状态不足，再在游戏中提供只读状态/完成事件或运行内计数证据，避免靠猜测、固定等待或旧存档结果判定。Fortuna 当前为有效输入、实际关卡完成和水果已切割增加了观察点，这些观察点目前也仅对 Editor 自动化编译。
5. 编写游戏准备/引导/玩法/结算子流程库，在“游戏接入”绑定四个阶段及正常入口；框架负责组合通用主流程。明确进入条件、完成条件和返回值；清理仅释放本次自动化资源。快速通关、指定关卡、清档、云控注入都不是所有游戏的强制接入项，按专门场景需要另行提供。

当前框架通用业务封装已抽出，新游戏不必复制提现/框架奖励操作，但仍需验证自身启动、引导交接及页面入口是否满足子流程前置条件。仅一款游戏实测，不能宣称已经跨游戏验收。现有 Editor 接口也不是未来 Android TEST 包的最终接口，运行时拆分仍需按 §1.15 实施。

**编排场景的通用程度**：

- **编排格式、基础节点与执行规则通用**：所有接入游戏使用同一种表达方式，这不代表每份 JSON 都能在任意游戏上运行。
- **框架功能子流程可设计为有前置条件的通用资产**：例如“在提现入口可操作时进入提现页 → 打开规则 → 关闭规则 → 返回”。需要统一框架动作/状态，并声明能力版本、进入页面和完成状态；游戏自定义入口通过绑定解决。框架内部云控分支在该子图维护，实际未启用功能不能伪装成已测试成功。
- **玩法/新手引导子流程按游戏维护**：例如 Fortuna 发刀和波次流程，不能原样用于合成或消除；即使都叫“完成一关”，也要由各游戏提供符合约定的实现或子流程。
- **完整端到端场景通常是组合资产**：启动绑定 + 游戏前置/引导与玩法子图 + 框架功能子流程 + 通用留证收尾。结构可做模板，游戏相关部分仍需绑定或替换。

本轮评审时，Fortuna 的 `game_smoke.json` 是真实游戏专属组合案例，不能直接跨游戏运行：子图嵌入同一文档，玩法及启动均绑定 Fortuna。后续按 §1.22 已将通用素材场景迁入框架，并实现项目游戏库和阶段槽位组合；独立通用任意子图库、能力版本与跨端类型契约仍未实现。

现已采用“框架基础能力 + 框架业务能力 + 游戏能力”组合注册，重名与命名空间冲突在运行前拒绝，框架不反向引用具体游戏代码。能力版本检查仍待跨端契约明确；通用素材场景已按 §1.22 提取；是否建立更广泛的共享子流程库，由第二款游戏接入后的实际复用量决定。

### 1.20 游戏接入文件与必要改动说明（2026-11-06）

当前游戏新增的 `Editor/Automation` 为玩法适配代码和独立 Editor 程序集，`GameMain/AutomationFlows` 为编排工具保存的流程数据，不是另一个 Unity 场景。适配器负责将具体游戏操作和状态暴露给节点；JSON 负责组合调用、分支、等待、断言和录制。`.meta` 是 Unity 资源身份文件，应与对应文件一起保留。

迁移前的 `game_smoke.json` 是当时“Fortuna · 引导通关与提现完整测试”在磁盘上的保存文件：编排界面读取它画出节点和连线，编辑保存时写回它，点击运行后执行器按其中的流程执行。内容包括启动场景/适配器绑定、主流程及子流程、节点参数和分支连线、节点位置与录屏设置。当时案例组织为正常启动 → 开始录屏 → 按实际状态处理引导 → 重复正常玩法直到本次通关 → 结算及提现页/规则浏览 → 截图、停录与清理。它保存的是测试步骤定义，运行结果另存于 AutomationOutput；文件名是早期命名，实际已是完整案例。通常通过编排界面维护，无需手写 JSON。

其他游戏若需自动完成自身引导和玩法，也需提供对应适配器并配置自身启动入口/玩法流程；无需复制编排工具、录屏和框架提现等共享能力。程序集引用按游戏实际程序集调整。完整 Fortuna JSON 不能原样跨游戏使用；共享框架能力已可复用，当前已按 §1.22 实现框架模板与独立游戏库的跨文件组合，任意共享子图库的依赖/版本管理仍未实现。

不要求每个游戏照搬三处玩法源码修改。优先使用游戏已有公开状态与事件；只有缺少可靠的操作/完成证据时，才增加最小只读属性或正常流程计数，禁止用测试逻辑代替真实通关。本次三处改动分别用于排除已切水果、确认有效输入、确认本次整关完成，均仅在 Editor 自动化宏下编译。当前方式属于需要少量代码接入的自动化，编排工具尚不能自动理解任意游戏玩法。

### 1.21 通用场景的归属与游戏绑定（2026-11-06，设计澄清）

用户期望编排好的通用场景由框架统一维护，无需每个游戏复制一份；场景不必须位于游戏工程。此前把当前案例的落盘位置解释成游戏接入必需项不够准确：通用性取决于节点依赖的能力契约和绑定方式，而不是 JSON 所在目录。

目标分层：框架维护通用主流程及框架业务子流程；游戏提供自身操作/状态和必要的专属引导/玩法子流程；项目接入信息绑定正常启动场景、游戏适配器及游戏阶段实现。仅引用框架能力的流程可作为框架共享资产；包含游戏阶段的通用主流程应调用约定的阶段能力或可替换子流程，不能直接写死 Fortuna 发刀、波次或首关引导步骤。简单游戏可以由适配能力实现阶段，复杂引导/玩法仍应保留可编辑子流程和业务分支。项目绑定不等于恢复此前已移除的多运行配置功能。

本段讨论时的实现尚未达到这个目标（后续实施见 §1.22）：FlowStorage 固定保存到 `Assets/GameMain/AutomationFlows`，管理页只扫描该目录；当前 JSON 同时包含 Fortuna 的 Adapter、Scene、专属玩法和框架子图。把文件移到框架不能自动解除这些耦合，现有管理页也不会自动列出框架内文件。后续实现应支持框架场景发现、独立项目绑定和游戏阶段替换；框架包只读时不能直接写包缓存，应提供明确的自定义副本或在框架源码工程编辑。现有真实案例在迁移验证前保留，本轮仅澄清设计与记录差距，未迁移文件或宣称已支持跨游戏运行。

### 1.22 框架通用录屏素材流程（2026-11-06，已实现）

本轮实现通用素材场景：正常启动、录屏、游戏准备/引导/玩法/结算、框架奖励与提现规则浏览、截图停录和失败清理。主流程及框架子图随插件发布，不能含 Fortuna 类型、场景路径、飞刀或波次条件。游戏阶段以声明输入/输出的子流程槽位接入；游戏工程仅维护自身子流程库、适配器及项目接入信息，不复制整份框架流程。未知/未绑定阶段、输入输出不匹配、递归或能力缺失须在启动前失败。

插件根目录由 `PackageInfo.FindForAssembly` 获取 assetPath/resolvedPath；支持框架源码工程、UPM 本地目录、嵌入包及发布包，不拼接版本号、不读取固定 Library/PackageCache 路径。发布资产放在包根 Assets 内的 Editor 自动化目录；框架内置场景始终只读，可另存项目自定义副本。项目接入信息和录屏覆盖存于 ProjectSettings，游戏子流程存于游戏 Assets；设置和运行均不得写插件源目录或包缓存。保留旧 schema 2 场景读取，不恢复多运行配置界面。运行保存组合后的完整快照，后续修改插件或游戏库不改写历史运行证据。

验收需包含现有水果游戏真实运行、未接入/契约错误拦截、内置只读与本地录屏覆盖、以及打包安装后的资源发现和组合验证；验证发布安装不等于实际发布，不提交、推送或发布版本。

实际入口为 `Tools → 自动化编排 → 通用 · 录屏素材`。管理页分别提供“游戏接入”“编辑游戏子流程”“查看通用流程”和“录屏设置”；内置结构只读，编辑游戏库只保存游戏图。项目绑定为 `ProjectSettings/IncentiveAutomation.json`，Fortuna 游戏库为 `Assets/GameMain/AutomationFlows/fortuna_gameplay.json`（5 图、31 节点），旧 `game_smoke.json` 已删除。运行组合为 17 图、112 节点，并保存完整快照及框架实际来源。其他游戏可复用同一主流程，但须实现自己的游戏适配器及四阶段子流程；不承诺无需适配即可自动通关。

### 1.23 当前全流程与后续工作总表（2026-11-06）

本节作为当前阶段的统一摘要；§1.22 保留实现与验收细节，后文早期设计不代表已经实现。当前已完成 Unity Editor 内的通用素材录制闭环；仍在本地联调，未提交、推送或发布插件。TestBench 尚不能导入执行当前图。

**使用流程**：

1. 游戏安装框架和 Recorder 依赖，测试配置启用 `ENABLE_AUTOMATION`。开发时可本地引用；发布包使用 Unity 查询的包根定位同一套资源。
2. 打开 `Tools → 自动化编排`，选择“通用 · 录屏素材”。场景管理负责选择、接入、运行/停止和结果入口；节点编辑与只读运行过程分别打开。
3. 每个游戏在“游戏接入”绑定正常启动场景、游戏适配器、游戏子流程库和四个阶段。准备返回 context；引导返回 result；玩法与结算接收 context 并返回 result。没有引导可以明确返回无需处理，不能把未实现的玩法当作成功。
4. 通过“编辑游戏子流程”维护本游戏的图，通过“查看通用流程”查看框架图。共享图只读；需要自定义主流程时复制为项目场景。添加功能优先封装子流程，连续按帧策略留在动作内部。
5. 在“录屏设置”调整尺寸、帧率和目标码率；默认 1080×1920 / 30fps / 20 Mbps、H.264 High、无音频。内置场景覆盖写项目绑定，自定义场景写自身 JSON；均不写包缓存。
6. 点击运行后，先组合模板与游戏库，检查结构、阶段契约、引用/递归、动作/状态和入口。通过后保存完整快照，设置正常入口并自动进入 Play Mode；launch 节点确认已启动，随后开始 Recorder，再等待游戏/框架初始化。
7. 游戏准备并记录当前起点 → 等待框架 Loading/首屏稳定，正常处理启动时遗留的框架引导 → 按实际状态执行或跳过游戏引导 → 游戏正常操作直到本次整关完成 → 游戏结算与框架奖励 → 按当前引导状态进入提现页 → 查看规则并返回 → 截图 → 停录并校验视频 → 清理并退出 Play Mode。具体节点顺序以运行快照为准。
8. 查看报告及 `AutomationOutput/<run_id>/`：组合图快照、节点/分支记录、MP4、PNG、片段索引和清理信息。绿色表示执行通过，蓝色运行中，红色失败，黄色取消；未经过节点不算覆盖。生成目录可在停止后删除，源流程及游戏存档保留。

**文件和能力归属**：

| 归属 | 内容 | 新游戏是否需要实现 |

| 框架 | 编排工具、图引擎、通用主流程、框架引导/奖励/提现/规则动作、输入宿主、录屏留证及清理 | 直接使用；新增通用框架业务在框架维护 |

### 1.24 项目副本编辑与改名（2026-11-06，修复约定）

框架内置主流程只读，复制到项目后的 schema 2 场景必须可以编辑主流程及场景名称；`UseProjectBinding` 只表示继续绑定游戏阶段，不能作为项目副本只读的依据。管理页明确区分“编辑主流程”和“编辑游戏子流程”，复制成功后选中新副本并打开主流程编辑。游戏子流程编辑模式浏览到框架共享图时仍只读，不能把此窗口当作主流程编辑器。

### 1.26 节点类型、人工创建步骤与开发边界（2026-11-06）

当前有 12 种基础节点，业务能力通过“操作”复用，不为每个按钮新增节点类型。

| 节点 | 用途 / 人工配置 |
|---|---|
| 开始 | 每张图的入口，每图一个 |
| 启动应用 | 主流程从正常游戏 Scene 启动 Play Mode；子流程不重复启动 |
| 操作 | 下拉选择已注册动作，填写该动作参数；截图也是操作 |
| 等待条件 | 状态键、比较方式、目标值、超时；完成/超时出口，未知状态不当作 false |
| 等待时间 | 固定毫秒延迟，仅用于节奏缓冲，不证明业务成功 |
| 条件分支 | 状态比较，连接“是/否”两条路径，适用于引导和云控等 |
| 结果校验 | 检查实际结果，不满足即失败 |
| 调用子流程 | 选择功能图、传入参数、接收返回；不允许递归 |
| 重复子流程直到条件满足 | 选择子图、结束条件、次数上限和总超时；用于逐步玩法操作 |
| 录制 | 开始/停止 Recorder；尺寸/帧率/码率在管理页录屏设置 |
| 片段标记 | 对同名片段标记开始/结束；记录边界，尚不自动裁切视频 |
| 结束 / 返回 | 主流程结束；子流程返回已声明的字段 |

**在已接入的游戏中创建场景**：

1. 素材需求优先选择通用流程直接运行；需要改变整体业务顺序时在管理页复制场景，在列表改名，再编辑场景流程。复制主流程仍绑定共用游戏库，不会复制独立游戏阶段库。
2. 完全独立的流程可点“新建”，生成开始 → 启动真实游戏 → 结束骨架；默认借用项目已配置的 Scene/Adapter，但不自动导入完整引导/通关子流程。没有项目接入信息时在右侧场景设置及高级设置指定入口/适配器。
3. 从“添加业务步骤”选择已注册动作，从“基础控制节点”添加等待/分支/校验等，拖动端口调整顺序和是/否出口；删除旧直连后再接入新节点。把功能细节放到子流程，主图仅调用模块。
4. 配置操作参数、状态条件与超时，子图需声明并传递输入/返回，引用值采用 ${参数名} / ${返回前缀.字段}。需要录屏时显式加入开始/停止和就绪校验；新建骨架并不自动录屏。
5. 保存（同时结构校验）→ 返回管理页 → 设置录屏参数 → 运行（完整预检）→ 查看真实路径、失败节点、报告及未覆盖分支。按实际存档/云控继续补测。

**是否需要改代码**：已有动作和状态足够时，添加节点/连线/分支只改编排数据，无需开发。新增游戏操作/状态需在游戏 IFlowGameAdapter 中实现并声明；框架通用操作在 IFlowFrameworkProvider 中实现，不放回游戏适配器。只有新增执行语义（如尚未支持的并行机制）才考虑增加基础节点、校验器与执行器，而非普通业务节点扩展。

**当前易用性评估**：已有场景改顺序/参数较容易；从零编排多分支或接新游戏需要开发理解业务状态和时序。操作已有中文下拉及默认参数，但状态键、比较值、变量引用与接口契约仍有手填和技术门槛，暂不能称为非技术人员完全无代码工具。后续可按需要补状态选择器、能力参数说明、阶段模板及更精确的节点级错误定位；这些属于建议，尚未实现。


### 1.27 图形编排是否保留：历史评估（2026-11-06，方向已由 §1.28 取代）

本节保留当时的评估依据，不作为当前实施计划。2026-11-09 用户明确后续全部由 AI 编排，因此不再建设本节建议的业务模块编辑器或高级节点编辑入口。能力类型/前置条件/结果描述仍有价值，用于 AI 维护、配置校验和诊断，而非为人工编辑表单建设完整平台。§1.25 为当前尚未迁移的实际界面。

**结论**：保留可视化流程及运行追踪，降低底层自由连线图在日常操作中的优先级。建议定位为“模板驱动的业务编排 + 开发维护的游戏能力 + 可下钻的执行图”。如果仅服务一名开发且流程长期固定，代码脚本 + 只读执行图会更经济；用户需求包含多游戏、业务分支、模块组合、可视化追踪，因此分层编排更匹配。保留的理由是这些需求，不是已投入成本。当前不建议继续投入完整通用低代码平台、完整行为树语义或第二套 TestBench 图编辑器。

| 方向 | 价值 | 主要代价 / 判断 |
|---|---|---|
| 全部代码，图只读 | 复杂策略易实现，版本差异易审查，适合固定流程的开发团队 | 常规流程调整依赖开发；业务分支与模块组合对使用者不直观，可作为条件变化时的退路 |
| 所有人操作基础节点、字符串和自由连线 | 表达自由、执行细节直观 | 把编程复杂度搬到画布，维护大图成本高；不建议作为日常默认入口 |
| 模板 + 业务模块，保留高级节点编辑 | 日常运行简单，已有能力可组合，复杂细节可下钻 | 需要少量能力描述和模块封装工作；推荐，分步验证价值 |
| 主要依赖录制回放 / AI 生成 | 可以辅助生成已有能力范围内的草稿 | 单次记录不能得出未发生分支、真实完成条件或跨游戏策略；作为后续辅助手段，不作为当前核心依赖 |

**当前难点及改进落点**：现有 FlowActionDefinition 只有 ID、名称、字符串默认值和执行函数，StateKeys 仅状态字符串列表；没有完整的参数/返回/状态类型、中文用途、前置条件、取值选项或版本声明。多层子图已有，但调用者仍需理解 context、返回前缀与异步发起后等待完成的配对。因此只做颜色、缩放或拖宽不足以降低人工编排门槛；先补能力描述，再由描述生成选择框和参数表单。

建议每项动作/状态/模块逐步补充稳定 ID、中文名称、归属/分类、参数类型/默认/范围、返回字段、状态类型/可选值、前置条件及完成/失败含义。优先覆盖现有模板实际使用的能力，保留旧 ID 及旧数据兼容，不先造泛化动态节点插件系统。长动作最终应有明确的进行中/完成/失败/取消语义及进度证据；当前异步动作仍是发起 + 状态等待，不能把建议误写为已经具备跨端长任务接口。

**建议的三个使用层次**：

1. 日常管理：选择“通用录屏素材”等场景，设置录像及模板确实需要的少量业务参数，运行/停止、查看结果和失败路径。已接入游戏无须再次编排，也不恢复多运行配置选择器。
2. 业务编排：默认展示少量有业务意义的模块，如正常启动、进入可玩状态、完成当前关卡、奖励结算、提现页检查。可新增/排序模块、配置中文条件分支和结果校验。简单串行流程可采用步骤列表或自动布局，分支在图中展示；不要求每一步必须手工连线。框架能力、项目游戏模块在同一选择界面明确归属。
3. 高级编辑/诊断：保留现有基础节点图、子流程、参数传递和精确等待，供开发处理特殊逻辑、维护模块和定位失败。运行结果可逐层展开到实际动作、条件值、耗时和证据。复杂策略可以写在能力实现中，不要求逐帧计算和所有代码分支画成节点。

三个层次应共用一份流程定义、能力目录和运行报告；简化视图是相同数据的投影，不再维护独立“简单版 JSON”。只对可无损表达的结构提供简化编辑；包含高级结构的图切换显示不得丢连线、变量或执行规则，应保留结构并提示进入高级编辑。界面布局不成为执行契约。业务模块最初由现有 call 子图封装实现，不必增加基础节点类型。不要把整套业务封成无过程/无证据的大黑盒。

**推荐默认业务图（示意，尚未改界面）**：

正常启动 → 进入游戏可玩状态 → 完成当前关卡 → 完成奖励结算 → 浏览提现及规则 → 留证结束。

录制起止、清理等由素材模板预置，默认收起，执行图仍可查看；需要调整采集范围或失败验证的高级场景可显式编辑。提现入口或功能未满足时应按场景目标报告失败或明确未执行，不能默认跳过后宣称完整素材场景成功。条件要区分已知否值、未知、功能不可用、失败；根据实际云控选路不等于已覆盖所有云控组合。

**扩展职责**：

| 新需求 | 修改位置 | 业务使用者承担的工作 |
|---|---|---|
| 已有步骤改顺序/参数/条件 | 场景模块组合及参数 | 选择/调整模块，无需改游戏代码 |
| 新增可由现有能力表达的功能 | 功能子流程，声明其输入/输出和前置条件 | 添加该业务模块 |
| 新增框架页面/通用奖励或提现规则 | 框架提供者及框架模块 | 使用升级后的通用能力，不向游戏复制实现 |
| 新增游戏玩法/引导/真实结果观察 | 游戏适配器及该游戏模块 | 完成一次项目接入后复用 |
| 新执行机制（确需并行、抢占等） | 核心契约、校验、执行器及高级界面 | 需求出现后专项设计，不因普通业务扩展增加节点类型 |
| Editor 与手机执行 | 同一业务定义 + 各端能力与启动/采集绑定 | TestBench 初期导入/运行/看结果，仍需桥与协议实现 |

**新游戏的接入方案**：

- 开发先提供正常入口、就绪及本次运行基线、合法玩法输入/策略、真实完成/失败证据和清理，游戏专属引导和结算按需要实现。新游戏不应重复实现录屏器、图引擎、提现/框架奖励，也不要求实现水果游戏的发刀/波次接口。固定关卡的可靠步骤可以作为首版，不强制通用求解算法。
- 将这些能力组合成可供场景选择的游戏模块，按所选模板的契约绑定；接入界面由模板要求和实际能力生成检查项。应能明确提示缺的是代码能力、阶段绑定、资源还是运行条件，避免盲目画图才发现无法执行。
- 当前通用素材模板的 prepare/tutorial/play/settlement 四槽继续兼容，但不固化为所有场景/玩法的永久通用顺序。引导与玩法可能交错（当前 Fortuna 的引导只先触发首步，玩法阶段继续验证自然结束），应允许游戏模块负责完整目标和内部交接；其他模板可以要求不同模块，不强制硬塞四个阶段。契约调整需显式兼容迁移，不静默改变现有图语义。
- 游戏模块定义可共用，单个场景应只调整实例参数；修改共用定义应提示影响范围。确需独立策略变体时显式创建变体并绑定。当前只有项目级阶段映射，尚无完整的单场景独立库/版本管理，不宣称已经支持任意变体。
- 插件发布仍只携带通用能力/模板；游戏入口、适配器和游戏实现留项目中，配置不写 Packages/PackageCache。跨端需要先规范能力/数据类型和异步完成/取消，再接执行端；界面外观本身不能保证 JSON 可直接给 TestBench 运行。

**建议推进顺序与验收**：

1. 先接第二种明显不同的真实玩法，形成接入清单和最小可靠流程，检验框架是否仍需修改。稳定共性后再决定哪些模块/阶段应标准化，避免只围绕水果游戏做通用架构。
2. 基于两款游戏实际用到的能力补描述/类型/状态选择器和字段校验；优先消除手填状态键及 ${...} 的日常使用需求，验证当前数据无损往返。

**素材参数建议（待实施，以下为语义示例，不是当前可运行的 JSON）**：

```json
{
  "scenario": "material_capture",
  "start": { "mode": "specified_level", "level": 10 },
  "playPlan": [
    { "outcome": "win", "count": 2 }
  ],
  "recording": { "width": 1080, "height": 1920, "fps": 30, "bitrateMbps": 20 }
}
```

- 从第 20 关开始：改起始关卡值即可，不改图或复制整套流程。
- 不需要失败素材：目标序列只含 win；需要“先失败一次，再完成两关”：使用 fail × 1 → win × 2 的有序目标。相比单一布尔开关，这能明确失败发生的位置和次数，避免后续再加一批互相影响的开关。
- win 的 count 是本次真实通关并完成所需结算的次数，不是点击次数；fail 的 count 是本次真实关卡失败的次数。失败后停留、重试或退回、胜利后是否自动进入下一关，由游戏能力按实际游戏实现，记录每次实际关卡号，不能假定所有游戏都是失败留关、胜利加一。
- 目标顺序决定实际拍摄路径，并不表示分支全覆盖。关卡号采用玩家看到的编号，游戏适配器负责和内部索引映射。
- 起点未配置时兼容现有“沿用当前存档”。指定起点需要显式关卡准备能力：可利用正常选关、测试入口或独立测试存档，具体方式按项目实现并记录。指定起点是新需求，不再把早期“不支持跳关”作为永久限制；准备动作不计为正常玩法通关。
- 默认不直接改写用户当前存档。独立测试存档/已有存档快照及异常恢复机制需在启用状态注入前落地；若项目只能修改现有存档，必须先明确说明并取得对应授权。不能只把 level 字段写入配置就声称准备完成；进入目标关后要读取游戏实际状态验证。
- 未接入起点准备/失败策略/多关继续能力时，在启动或写存档前给出缺失能力错误；不降级为当前关、不跳过目标，也不使用直接结算/直接设置失败状态冒充游戏过程。

**预期游戏失败与执行故障必须分开**：

- 目标是 fail，且通过正常玩法输入确实观察到本次失败、失败页面/处理结果符合要求，可以判定该目标通过。成功路径意外失败则是目标不符。
- 超时、操作没有被接受、崩溃、未知状态或能力错误仍是自动化故障，不能满足 fail 目标。报告分别记录任务状态、预期胜负、实际胜负、实际关卡、证据与原因，不把 ExpectedStatus=failed 当作游戏失败实现。
- 每次尝试重新记录输入/胜负/结算基线，不能用前一关或前一次尝试的成功标志满足下一次目标。当前 Fortuna 适配器只观察一次完成基线且把 GameOver 当作异常，需专门扩展后才能执行上述计划。

### 1.30 可组合业务子流程、接口跳关与广告成功策略（2026-11-10，实施约定）

用户要求按完整业务边界拆分并调整当前实现：游戏成功（加载目标关 → 正常玩法成功 → 结算/宝箱）、游戏失败（加载目标关 → 正常玩法失败 → 复活/重玩等页面按钮）、提现（正常入口 → 输入字段 → 点击提现）。AI 维护模块内部的图/能力，项目配置只组合模块实例、顺序、启停及参数；界面可提供模块参数设置，不恢复节点自由编辑。一个模块可多次实例化，使用稳定且唯一实例 ID；修改或删除实例不改变公共模块定义。

- 配置按场景 ID 存在项目绑定的 Plans 中；每个模块实例声明 Id、Flow、Enabled、Args。框架提供通用模块库，游戏库提供准备/引导/玩法/结算/加载目标关/失败操作；按实际引用组合，未用到的阶段不要求游戏实现。新增普通业务子流程可在库中声明模块及输入参数，无需新增基础节点类型。
- 成功/失败模块参数 level=0 表示当前关，正数表示界面显示的目标关；连续两关可配置两个成功实例（例如 10、11）。超过目标关时按 on_ahead=delete_account 进入服务端删号；设置 stop 则拒绝回退。用户已确认跳关是逐关调用现有 /merge/coin/level/up，而非虚构测试接口。每次检查成功响应及 user/info 的权威关卡，加入请求间隔，目标相同不请求；失败/超时/取消不自动重发有副作用的请求。
- 删号仅对当前实际测试环境开放，保留现有测试账号标识/国家设置；后端明确成功后才清本地数据。请求失败不采用旧调试按钮“失败仍清本地”的兜底。通过显式重启节点保存执行检查点、退出 Play Mode、从正常入口重启；检查点在删号之后，不重复删除请求。录制跨重启分为有顺序的多段产物，不伪装成无中断视频。
- 所有自动化场景广告使用成功策略：在测试运行会话内从框架统一广告入口模拟成功回调，奖励广告 isReward=true，插屏/开屏走正常关闭回调，不播放 SDK/H5、不制造真实展示/收益记录。策略在正常启动场景之前生效，结束、失败、取消后释放；宏隔离，不影响正常手玩及正式构建。报告明确为模拟广告成功，不代表真实广告验收。
- 页面操作默认停留 1000ms（可调范围 300–10000ms），每次解析按钮后等候并重新检查遮挡/可点击；输入事件处理后维持本次自动化鼠标为当前设备，防其他鼠标事件抢占导致漏输入；会话使用临时 InputSettings 允许后台输入并在清理时恢复，不写项目输入配置或 Editor 主题；文本输入与后续点击也等待。未知弹窗不任意关闭；加载/网络等用真实状态完成条件，不以固定停顿替代成功判断。
- Fortuna 成功策略按当前盘面角速度和飞刀正常飞行速度预测命中时机，直到本次真实通关，不配置固定发刀次数。Fortuna 失败策略优先等待空隙，若当前水果排列持续覆盖刀路，则正常快速连续发刀来消耗刀数；不改刀数、速度、碰撞或胜负标志。失败由正常玩法输入造成，GameOver 必须有本次尝试证据；发刀等待期间若 UI 遮挡出现，动作返回 deferred，由外层框架弹窗流程处理后重新观察；不增加真实输入或发刀完成计数。只有确认本次正常输入计数未增加时，允许重新观察后补发未被接收的飞刀输入（最多 3 次）；已接受输入、UI 业务按钮和网络提交不重放。输入故障/超时仍是自动化失败。复活与重玩在框架 LevelFail 页面按配置正常点击，并等待页面关闭和游戏恢复。游戏专属失败页面应由该游戏模块实现。

- 预检校验模块、参数类型/范围、引用、阶段契约及能力；编译为原有 schema 2 不可变快照，节点可下钻、按调用路径区分多次执行。图查看入口不增删节点/连线、移动节点、修改属性或保存。既有用户副本及未保存草稿不静默覆盖；包内模块通过 PackageInfo 定位，配置不写包目录。

### 1.47 Editor后台运行与并行操作的边界复核（2026-11-11，仅诊断/讨论）

用户反馈运行时切到其他页面操作有时出问题。源码确认游戏设置和会话驱动均已开启runInBackground；这仅允许继续执行。Unity官方UUM-91847（https://issuetracker.unity.com/issues/3601/low-fps-in-the-game-view-when-the-editor-window-loses-focus）确认2022.3.54f1起Editor应用失焦主动限速，当前2022.3.62f3受影响，无设置关闭此限速。与§1.43一致，允许后台执行不等于后台全速或可靠并行工作。

另有独立的输入隔离缺口：AutomationSessionDriver临时使用IgnoreFocus与AllDeviceInputAlwaysGoesToGameView，创建自动化Mouse，并在其InputBusy期间MakeCurrent；未将真实键鼠与自动化设备对UI/游戏输入的作用完整隔离。FlowInputSession每次点击或输入仍FocusGameView。特别是在Unity中操作其他面板时可能产生输入或焦点干扰；切至其他应用时，具体硬件事件是否进入Unity取决于系统/后端，不能声称会把外部应用点击全部收到游戏中。IgnoreFocus仅关闭输入焦点重置/禁用，不会授予操作系统后台键盘采集能力；它还可能保留失焦前的按键状态（Unity官方ISXB-1730说明），本轮未做该触发的真实复现，不能把风险写成已确认的失败根因。

读取用户当前批次2026-11-11_11-23-53已有记录：ID填写、提交与completed节点通过，outcome= rejected触发校验失败，运行末尾game_focused=false；BR已通过。失焦与拒绝同时出现不代表因果关系，拒绝原因须查实际请求/返回，不能将此条写成漏点或后台超时。批次仍在进行，本轮未修改执行代码或重启/停止它。

### 1.48 自动化输入隔离与焦点处理的改造范围（2026-11-11，方案，未实施）

框架改造项：
1. AutomationSessionDriver管理显式的自动化会话与专用输入设备，创建时即可用于玩法/UI，并验证虚拟设备后台可用性；减少依赖全局Mouse.current及短时MakeCurrent争抢。提供会话输入入口，按输入消费者隔离，不能全局禁用真实鼠标/键盘，避免影响Editor正常操作。
2. 会话内为InputSystemUIInputModule准备专用或克隆的UI输入动作配置，仅接收自动化设备，屏蔽真实点击/滚轮/导航/提交对游戏UI的作用。保存原引用/动作/设备过滤，支持场景切换和运行期间新建的EventSystem；退出时恢复，不改场景/Prefab/项目输入资产。具体绑定API与旧模块兼容在实现时验证。

4. 文本输入保留页面停留、逐字节奏与业务校验，同时保护选区/光标/提交状态。当前Unity UI InputField.OnUpdateSelected会通过Event.PopEvent处理键盘事件，单独限制UI InputActions不足以宣称文本已隔离；需验证会话范围的输入框事件控制方式，不能只在下一帧覆盖文字或清空全局键盘事件来掩盖干扰。UI丢焦、中文输入法、Esc/Delete/回车和选中对象变化须纳入验证。

## 2. 方案总览

当前已实现链路（2026-11-10）：AI 维护模块图与能力 + 项目业务模块配置/游戏绑定 → 组合后的 schema 2 场景快照 → `FlowEditorRunner` / `FlowEngine` → `FlowEditorHost` → 框架/游戏能力、共享正常输入、Recorder → 只读状态与执行证据。

当前素材实现和验收以 §1.31–1.44 为准；不再依赖人工图编辑。真实逐关升级及领奖已在隔离测试身份验证，其他游戏、删号重启及跨端能力仍需单独验收。

后续目标链路（尚未实现）：同一业务图及端绑定 → TestBench 图执行器 → 设备 Host → 手机 TEST 包能力桥、adb/scrcpy → 运行报告与证据。Editor 与手机共享动作/状态契约，宿主生命周期、输入和录制实现分别适配。具体评估及建议见 §1.15。

- **文件即契约**：场景是 JSON 数据，编辑源与运行快照可分别留存；当前格式尚未完成跨端规范化。
- **流程与平台能力分开**：只有执行端满足该场景所需能力时才承诺双端运行。
- **通用编排、游戏特色化实现**：功能由子图组织；新玩法通过游戏能力接入。

## 3. 需求场景

### 3.1 素材录制（v1 优先）

- 自动操作游戏 → Editor 中录制（Unity Recorder 高画质）→ 按标记切段 → 导出给素材同学
- 多国家/多版本批量产出（矩阵展开）
- 要求“像真人玩家”：拟人化操作、画面干净（正式包或无调试 UI）

- 真机 TEST 包上执行用例：页面跳转、按钮点击、状态断言、日志断言
- 断言三轨：日志规则引擎（TestBench 已有）+ 桥状态 + 截图留证
- 失败六分类归因：产品 Bug / 自动化 Bug / 环境 / 网络 / 数据 / 崩溃 / 未知

### 3.3 双端一致

目标是同一业务流程由 Editor 与真机执行器消费，执行前检查所需能力。当前只接通 Editor，仍需按 §1.15 规范化格式、提供端绑定及运行时桥。Editor 专属实现不承诺原样在真机执行。

## 10. 场景文件格式 v1（JSON 契约）

以下为已有骨架对应的格式草案，尚未冻结。启动配置 `launch` 及操作的 `repeat_count`（1–1000）/`repeat_interval_ms`（非负毫秒）已加入模型；操作前后条件先由独立等待/校验步骤表达；未实现类型不能因校验通过而视为可执行。

### 10.1 Schema 结构

```json
{
  "schema_version": 1,
  "kind": "shoot | case",
  "id": "唯一 id（文件名 = id.json）",
  "name": "场景名",
  "description": "可选",
  "launch": { "enter_play_mode": true, "ready_state": "framework.ready", "timeout_ms": 30000, "exit_play_mode": true },
  "params": { "country": { "type": "enum", "values": ["ID","BR"], "default": "ID" } },
  "setup": {
    "session":  [ SetupBlock... ],   // 跨场景缓存（切国家+重启等昂贵操作）
    "scenario": [ SetupBlock... ]    // 每场景执行（云控注入/清数据/广告模式）
  },
  "steps": [ Step... ],
  "teardown": [ TeardownBlock... ],
  "matrix": [ { "country": "ID", "ad_mode": "none" }, ... ],
  "output": { "naming": "{scene}_{country}_{segment}_v{version}", "dir": "materials/{scene_id}" },
  "endpoints": { "editor": { "required_caps": ["unity_recorder", "editor_cmds"] } }
}
```

### 10.2 SetupBlock

```json
{ "type": "setup", "op": "switch_country | cloud_config | user_reset | ad_mode | app_restart | custom",
  "scope": "session | scenario",
  "params": { "country": "{country}" },
  "sets": ["country.current"],                    // 冲突检测声明
  "verify": [ { "on": "state|page|log", "key": "...", "op": "eq|neq|gte|lte|contains", "value": "..." } ],
  "depends_on": [], "idempotent": true, "cacheable": true,
  "on_fail": "abort | continue", "comment": "" }
```

### 10.3 Step 类型

| 类型 | 字段 | 说明 |
|---|---|---|
| segment | ref, params | 片段引用（`library/xxx.json`） |
| wait | on=time/stable_frame/event/state/page, ms, key, eq, timeout_ms | 时间等待须非负，条件等待须显式配置超时；仅表示编排能力 |
| action | op=click/invoke, target, mode, action_id, timeout_ms, repeat_count, repeat_interval_ms, on_unexpected_popup | 操作与有限次数重复；点击路径需区分覆盖范围 |
| record | op=start/stop, preset{width,height,fps,codec}, if_running | 录屏控制 |
| mark | op=begin/end, segment | 切段标记（区间对） |
| editor | cmd=time_scale/camera/hide_ui, value | 编辑器专属 |
| inject | key, value | 中途注入（少用） |
| assert | on, key, op, value | Editor 最小闭环即支持基础状态/页面结果校验；完整日志断言后续接入 |
| switch | on, key, cases, default, log_decision | 运行时分支（v2 实现） |

### 10.4 校验规则（已实现于 ScenarioValidator）

- 结构校验：schema_version/kind/id/name/params 合法性与 default∈values
- 步骤：id 唯一；各类型必填字段；mark begin/end 配对（重复 begin、孤儿 end、缺 end 报错）
- 矩阵：行参数必须在 params 声明，且每个声明参数每行必填
- **冲突检测边界**：只比较 `sets` 能从 `params` 同名键明确取得的值；不能解析的写入不猜成空字符串，也不声称已证明无冲突。动作到实际状态键的映射由后续能力注册补齐。
- ID 采用 1–96 位字母、数字、下划线或连字符，以字母/数字开头；新增步骤生成唯一身份，移动不重新编号。
- 显式 null、非法等待时长/超时、重复步骤 ID、无效录制参数、录制区间外的片段标记以及准备依赖环均应报错；静态校验不证明动作可执行。

### 10.5 参数解析优先级

```
矩阵行 > 国家配置表 > params 默认值
```

国家配置表（数据，不进流程）：国家 → 支付方式/币种/档位规则等。新增国家 = 加一行，流程零改动。

## 11. 编排设计

### 11.1 三层准备（扩展设计）

简化版先保证单场景准备可重复执行且结果可验证，不实现跨场景缓存和断点续跑。以下分层与缓存是后续目标；重启、清档、切账号或切国家后的失效规则需先明确。

```
session 层：安装/重启/切国家+重启/等 SDK 初始化 → 一批场景只做一次，可缓存跳过
scenario 层：云控注入/用户重置/广告模式/清弹窗栈 → 每个场景执行
步骤内注入：中途改状态 → 显式 inject 步骤，少用
```

**五条原则**：
1. 分层可复用（session 层跨场景缓存，避免每场景重启）
2. 注入必校验（每个准备块带 verify，不通过即 abort，脏状态不进步骤区）
3. 静态可检（sets 声明 + 冲突/环检测，编排期消灭问题）
4. 安全重试（幂等性由动作实现保证；有副作用的操作超时后先核实结果，不能仅凭配置标记直接重试；断点续跑后续实现）
5. 全程可见（报告分“准备/步骤/清理”三段，变化有迹可循）

### 11.2 分支设计（后续扩展）

简化版只执行使用者预设的顺序、条件等待和必要的有限次数重复；不要求自主选择玩法策略。以下矩阵及运行时分支不作为首阶段交付内容。

```
80%：前置强制 —— 云控/国家/广告模式全部可注入，写两个前置不同的确定性场景，
     而不是一条带分支的流程（回归稳定根基）
     + 参数矩阵：同一模板 × N 组前置 = 批量 A/B（云控矩阵/国家矩阵）
20%：运行时 switch —— 条件源：state / page / log / event；
     log_decision=true 记录“第 N 步分支: 条件值 ← 来源”，失败可归因
探索 ↔ 回归：探索模式自由走分支并记录路径 → 稳定复现 → 固化成矩阵行 → 回归无分支
```

### 11.3 切段与输出（D11/D12）

- mark begin/end 具名区间对 → 段名进文件名
- 命名模板：`{scene}_{country}_{segment}_v{version}`（output.naming 可配置）
- 意外弹窗仅在预设明确处理规则时允许关闭并继续；未知弹窗保留证据并停止。发生恢复时记录过程，避免把已偏离脚本的素材直接视为成功。

### 12.4 节点画布与条件分支设计（按 §1.6 实施）

- 左侧节点库，中间可平移/缩放的画布，右侧选中节点属性；支持新增、拖动、连线、删除、定位校验错误，以及节点位置保存。
- 初始节点：开始、启动/准备、操作、等待、条件判断、结果校验、录制/片段标记、结束；先明确串行分支与汇合规则，循环以显式有限重复表达。
- 控制连线表示“接下来执行什么”；节点属性读取参数和运行上下文。第一版可先采用类型明确的字段选择，不要求同时引入数据连线或任意表达式语言。
- 条件分支由场景作者预先连接；执行器只判断预设条件。每个节点仅由控制流激活，业务动作不会因画布刷新或状态轮询而重复提交。
- 等待节点必须区分“条件已确定为 false”和“尚未取得结果”。条件未就绪先等待，失败/超时走明确异常策略。
- 正常分支汇合：任一选中的路径到达后继续一次；不是等待未被选中的所有路径。失败/取消后的停录与清理属于执行器保证的收尾，不能只依赖成功路径连线。
- 示例图：启动 → 等待初始化 → 准备条件 → 点击提现 → 等待本次业务分支结果 → 广告路径/无广告路径 → 汇合等待提现结果 → 校验预期 → 结束。广告路径中的绕过、Mock、H5 或真广告处理仍由场景策略限定。

云控与服务端条件的处理建议：

| 来源 | 准备阶段 | 执行阶段 | 验证边界 |
|---|---|---|---|
| 云控 | 指定覆盖值，声明生效时机并验证最终生效值；实际生效值可能经过缓存、默认值与其他条件计算 | 读取业务最终条件或该次操作的分支事件 | 区分覆盖配置的业务分支测试与真实云控下发/缓存测试 |
| 服务端功能开关/数据 | 测试环境的指定账号/数据、受控响应或 Mock；真实接口链路另设场景 | 等待并关联本次响应，按业务最终状态选择路径 | Mock 不证明真实接口、权限或联调已通过；本地注入不改变服务端实际权限 |
| 本地状态 | 准备余额、次数、进度等允许设置的数据并验证 | 结合本次运行状态判断 | 避免把上次运行的状态/成功日志用于本次分支 |

用矩阵分别覆盖开关开/关、成功/失败等已选组合，并为每次运行声明预期路径。以当前输入条件枚举为覆盖计划，不把一次运行经过某一分支当作覆盖所有业务条件。

### 12.5 功能模块与子流程（2026-11-05，本轮实现基础能力）

**用户提出的方向**：主流程将“提现流程”等功能作为一个节点，其内部操作、判断与等待在独立子图中维护。建议采用这一分层方式；它与节点流程图或行为树的选择是两个问题，并不要求先引入完整行为树语义。

建议按职责分层，通常先保持两到三层，不按每个页面机械拆分：

- **场景主流程**：启动/准备 → 调用提现流程 → 调用任务流程 → 校验与输出；负责本次目标、运行条件和完整生命周期。
- **功能子流程**：例如“执行一次提现”，内部包含进入页面、等待就绪、提交、观察实际分支、广告处理、等待业务结果及校验；复杂且可复用的广告处理可以继续抽为子流程。
- **基础动作与控制节点**：点击、等待、读取状态、条件判断、结果校验等。业务细节保留在合适层级，避免主图铺开所有节点。

“打开提现页”和“执行一次提现”应是语义明确的不同能力，不能因为页面名称相同就合并。只为整理画布而添加的分组可以折叠；需要独立维护、复用或调试的逻辑才抽取为子流程。拆分依据是完整职责与清晰边界，不要求所有节点都封装。

**子流程调用契约建议**：

1. 调用节点引用子流程定义，不是复制一份节点。当前同一场景文档内可多次调用同一份子图，分别传入金额、广告策略、预期路径等参数；不同调用实例的局部数据相互隔离。跨场景文件共享资产是后续扩展。
2. 明确进入条件与完成条件。例如运行环境已就绪且账号满足前置条件；调用返回时业务结果已确定，并说明停留在哪个页面。独立调试时也要显式准备或检查这些条件。
3. 区分业务输出和执行状态：实际路径、业务结果、流水号等作为输出；成功/失败、超时/取消表达本次调用的执行情况。预期的业务拒绝可作为正常返回结果供上层判断；无法取得结果或动作执行错误不能伪装成正常业务分支。
4. 主流程按子流程返回的摘要结果继续；云控、广告、请求响应等内部细节在子图判断。参数描述业务意图，避免把每个内部开关都暴露给上层，导致复杂度转移到属性面板。
5. 子流程默认不自行重启应用、清空全局状态或停止上层录制；确有需要必须在契约中声明。取消应传递到当前子流程，失败/取消仍由执行器保证必要清理；有副作用的提现操作不因调用失败自动重试。

**编辑与定位建议**：双击调用节点进入子图，用面包屑返回主流程；主图显示执行摘要，失败时可定位到“场景 → 提现调用实例 → 广告处理 → 等待回调”。同一子流程被调用多次时，运行记录需要区分调用实例，保留本次实际路径。修改共享子流程应能查看引用它的场景；保存/运行时校验引用缺失、参数不匹配与直接/间接递归调用。

**本轮落地范围**：节点版实现“主流程 + 可引用子流程”，支持输入参数、结果返回、进入子图和返回、基本引用校验。示例是主流程 → 提现 → 广告的三级结构。子图当前以独立 ID 定义在同一份场景文档内，多个调用节点引用同一份定义；跨场景文件共享子图资产尚未实现。不引入递归、并发、任意跳转、复杂继承或版本库。旧 `segment.ref` 草案与新图调用机制分开，未将旧场景标为已经迁移。

### 12.6 节点职责与设计顺序（2026-11-05，细节按案例落地）

用户提出先设计节点类型，并允许质疑、调整已有想法；随后要求参考类似工具，判断是否有必要借鉴或复用。建议先明确执行规则和最小节点集，再用实际场景验证，不一次性穷举所有业务节点。

必须区分三个概念：

- **通用节点类型**：动作、等待、判断、校验、子流程调用等，定义执行规则。
- **已注册动作能力**：打开页面、提交提现、配置测试条件等，由业务桥提供动作 ID、参数、完成条件和可用端。节点库可以将注册能力展示成“打开提现页”等易懂条目，底层仍使用动作节点；增加业务动作通常不需要增加一种执行模型。
- **业务子流程资产**：“执行一次提现”“完成一次任务”等，由通用节点和动作能力组合而成，可在节点库中以业务名称展示；底层统一为子流程调用，不为每个模块写一个编辑器专属节点类。

建议的最小节点职责清单（概念设计，不是已实现清单）：

| 类型 | 负责什么 | 示例及边界 |
|---|---|---|
| 入口 / 返回 | 定义本图开始与完成结果 | 子流程返回数据；异常退出不能冒充业务结果 |
| 动作 | 发起一个明确操作，按契约确认完成 | 点击提现、打开页面、调用允许的准备能力；操作已发起不等于业务成功 |
| 等待 | 等待时间、状态或本次关联事件 | 等待页面就绪、接口决策；有超时，不通过重复提交来等待 |
| 条件分支 | 对已取得的值选择预先连接的路径 | 广告 / 无广告；未知或读取失败不能当 false |
| 结果校验 | 判断是否符合本次预期 | 预期业务拒绝可以通过校验；校验未通过应明确失败 |
| 子流程调用 | 传参、调用独立子图并接收结果 | 调用提现流程、广告处理；隔离局部数据并保留调用链 |
| 录制与标记 | 控制录制、标记片段 | 开始 / 停止 / 标记可在界面显示为独立条目，最终类型粒度随案例细化 |

启动、环境准备、收尾是场景生命周期职责，不必机械地为每项创建一种节点类型。画布可以提供对应区域或能力入口，但启动前配置的时机及失败/取消后的必需清理要由执行器约束。有限重复仅保留明确上限的简单形式；并发、递归、任意脚本和通用表达式编辑器不作为首版前置项。

每种节点先写清输入/输出、完成判据、可连接出口、超时/失败/取消行为及重复执行风险。默认串行执行；分支一次选择一条路径；条件判断不自行等待或提交业务；等待不隐式重试动作。界面展示的业务名称与底层通用类型可以不同，不要求作者每次从空白动作节点手填技术 ID。

建议推进顺序：确定典型场景与执行规则 → 最小节点职责和子流程契约 → 用提现有广告、无广告及超时三个路径检查表达能力 → 设计主图/子图交互与必要的数据格式 → 再选择合适的技术组件并改造实现。图形编辑与真实执行分别验收。

## 13. 执行引擎设计

### 13.1 Editor 执行链路（已实现，零网络）

点「运行」→ 读取框架模板、项目绑定与游戏库并组合 → 校验图/动作注册及游戏环境 → 保存本次场景快照 → 设置正常启动场景并进入 Play Mode → 创建本地 Host 与图引擎 → 确认启动、开始 Recorder → 按图等待初始化、跟随真实引导、执行正常输入/整关玩法、分支、功能子图和校验 → 截图、停录 → 引擎保证清理 → 退出 Play Mode 并输出报告。

动作由 `FlowCapabilitySet` 分发到框架 `IFlowFrameworkProvider` 与选中的 `IFlowGameAdapter`，共用 `FlowInputSession`；录制/截图由 Host 提供。尚无手机 AutomationCore 或网络传输。当前 Fortuna 以正常操作通关，未使用快速通关准备；未知弹窗或失败如实中断，不以模拟成功兜底。片段时间来自 Recorder 帧数与实际帧率，自动裁切未实现。

### 13.2 真机执行链路（v2，目标规划，尚未实现）

```
TestBench 执行器 → 检查设备与目标应用 → 启动/重启应用
  → adb forward → DeviceTransport → AutomationCore 握手 → 等待初始化
  → 命令执行；断言三轨（日志规则引擎 + 状态回包 + 截图留证）
  → 录屏由 TestBench scrcpy 侧执行
  → 失败六分类报告
```

### 13.3 执行器状态机

最小闭环：`检查 → 启动 → 等待就绪 → 准备 → 步骤执行 → 完成输出 → 清理 → 成功/失败/取消`。进入 Play Mode 的域重载需要保留待运行任务上下文，避免重载后丢失任务或重复启动。

第一版失败默认停止并清理，不自动重试有副作用的操作。后续再实现经过验证的 retry/recover/goto 和断点续跑；步骤身份需稳定，不能依靠移动步骤后重新编号来标识同一步骤。

## 15. 素材录制方案

### 15.1 Editor vs 真机

| 维度 | Editor（Unity Recorder） | 真机（scrcpy） |
|---|---|---|
| 画质 | 无上限（4K/60fps+、任意比例） | 设备限制 + 编码开销掉帧 |
| 真实性 | 可能失真（桌面 GPU/无刘海适配/鼠标≠触摸） | 100% 真实 |
| 合规（投放） | ❌ 平台要求素材真实反映体验 | ✅ 天然合规 |
| 可控性 | 极高（时间缩放/相机/藏 UI） | 低 |
| 结论 | **内部用/特写镜头** | **投放素材必须真机** |

v1（Editor 优先）产出内部评审/特写素材；投放素材在 v2 真机链路补充。命名/切段机制两端一致。

### 15.2 拟人化（真机链路重点）

坐标抖动、间隔随机、swipe 分段插值模拟轨迹、偶发停顿——机械感是素材的大忌；参数做成场景/执行配置。

### 15.3 素材合规

正式包画面（无调试 UI）、清账号（防 PII 入镜）、音频版权注意；投放素材必须真机。

## 16. EditorTransport 健壮性设计（八条）

1. 域重载/进出 Play Mode：监听器自动重建，断线广播原因（`play_mode_exit`/`reloading`），对端自动重连并显示状态
2. 命令异常：全包 try/catch，只回错误码，绝不向主循环抛出、不弹窗
3. 命令超时：主线程队列每条命令带超时，超时回 `timeout` 并放弃
4. 长耗时命令（录屏）：异步 + 进度事件，不阻塞命令循环
5. 编译中（isCompiling）：拒绝新命令，回 `editor_compiling`
6. 端口冲突：探测 5100 被占用则自动换端口并告知对端
7. 空闲零开销：未连接时监听线程睡眠；宏关闭时代码不存在
8. 编辑器日常无感：全部代码在宏内，异常不打断编辑器

## 17. 自动化测试设计（v2，真机）

- **断言三轨**：日志规则引擎（TestBench 现有，命中 `[TAG]: message` 规则）+ 桥状态断言（state.get）+ 截图留证
- **失败六分类**：产品 Bug / 自动化 Bug / 环境 / 网络 / 数据 / 崩溃 / 未知——每条失败用例强制打标签；规则引擎命中 = 产品 Bug，桥超时/元素不存在先归自动化 Bug，流向不同处理人
- **两套件闭环**：确定性回归（Bridge+规则引擎）+ AI 探索（ARTEMIS/Midscene，v2 后）→ 发现 → 稳定复现 → 转确定性场景 → 进矩阵回归
- **确定性控制**（已核实的框架资产）：`WithdrawCloudConfig.DebugSetConfigJson`、`DebugResetNoticeShowCount`、`AdsCloudConfig` 静态开关、`TestConsole` 清档/切国家、测试服接口
